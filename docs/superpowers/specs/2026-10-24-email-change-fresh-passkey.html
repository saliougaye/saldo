A fresh passkey to change the email address

To start a change to a real email address, you must sign in with your passkey in the last 5 minutes. A stolen session cannot take the account this way.

Language Simplified Technical English (ASD-STE100) Extends docs/superpowers/plans/2026-10-19-change-email.md Date 2026-10-24
01

What changes

Saldo asks for a new passkey check before it starts the change of a real email address.

Since 2026-10-19, an account with a verified email can change it. The new address gets a link. The swap happens when the link is opened. The old address gets a notice.

Now the person must also confirm with a passkey. The passkey sign-in must be less than 5 minutes old.

Threat

A person with a stolen session can start a change to a mailbox that this person controls. After the swap, «recover by email» (/recover) lets this person register a passkey and take the account. The notice to the old address comes too late.

A stolen session is a cookie or a bearer token. The rule applies on a server with SMTP. A server without SMTP does not change a real address at all, and this does not change.

02

The rule

Only the start of a change to a real address needs a fresh session. All other actions stay as they are.

A session is fresh when its createdAt is less than 300 seconds old. The constant is FRESH_SESSION_SECONDS.

The sliding updateAge of Better Auth never changes createdAt. Thus a long-lived stolen session is never fresh.

The route POST /api/me/email and the Server Action requestEmailChangeAction both call startEmailChange. The function makes these checks in this order:

  1. Mail is off: answer 409 email_already_set, as today.
  2. The session is not fresh: answer 403 reauth_required.
  3. The address is unchanged: answer 400.
  4. The rate limit is reached: answer 429.
  5. Store the pending change and send the link: answer 202.

The freshness check comes before the rate limit. A refused request stores nothing, sends no mail, and spends no rate-limit slot.

ActionFresh passkey neededAnswer when the session is old

The phone

The phone app only fills a synthetic address. It never calls the real-address branch. Thus the rule does not affect it.

A bearer client that calls the branch gets 403 reauth_required. A phone session from the browser hand-off (/auth/mobile) starts right after a passkey sign-in. It is fresh for 5 minutes.

03

The flow

The form asks for the step-up one time, then it sends the same request again.

When the form gets reauth, it shows a sentence and a button. The button calls authClient.signIn.passkey(). The login page makes the same call.

The passkey verify step of Better Auth always creates a new session and sets its cookie. Thus the new session is fresh.

Note

The person must click the button. Some browsers, for example Safari, refuse a WebAuthn prompt that no click started. Thus the form never starts the prompt itself.

If the passkey sign-in fails, or the person cancels it, the form shows «not confirmed». Nothing changes.

05

Limits

The rule makes a stolen session much weaker. It does not remove every risk.

ItemLimit
Session under 5 minutesA thief who holds a session that is less than 5 minutes old can start a change. The thief cannot make a fresh session later without the passkey.
Synthetic addressAn account from before D32 can fill a synthetic address with an old session. This account has no real address to protect. This gap affects only such old accounts.
Old sessions stayThe step-up makes a new session. The library does not revoke the old sessions. A stolen session stays valid for all other actions. Revoking other sessions is out of scope.
No undo linkThe notice to the old address has no undo link. We rejected it. It is weaker, because the thief can use recovery before the owner reads the mail.

Words

The meaning of the special words in this document.

WordMeaning
