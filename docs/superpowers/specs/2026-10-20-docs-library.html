Saldo 0.8b · apps/site · Spec

The docs library

The guides that are now loose Markdown files become pages of the site, under /docs/. Each page renders from its file in the repository, so the site and GitHub always say the same thing.

Language Simplified Technical English (ASD-STE100) Extends specs/2026-10-18-marketing-site.html Roadmap 0.8 Decisions D53–D60 Date 2026-10-20
01

Scope

This spec adds a docs library to apps/site. It uses Starlight, the docs framework of Astro, in the same app as the landing page.

Today a visitor reads the guides on GitHub. The landing page sends the visitor there (D50). The library puts six pages on the site, in four groups, with search and a contents list on each page.

The Markdown files stay the source of truth. Nobody edits a copy for the site. A change to docs/self-hosting.md changes the GitHub view and the site page in the same commit.

In scope

Five Markdown pages: docs/self-hosting.md, docs/building-android.md, docs/building-ios.md, SECURITY.md, CONTRIBUTING.md. One Guide page from the app catalog. The index page /docs/. Search. The theme. The link changes on the landing page. The sitemap. Two headings in the Markdown, from Italian to English.

Not in scope

README.md (the landing page does its job). Plans, specs and ROADMAP.md. Languages other than English (D43). A version selector: there are no releases before 0.9. New guide text. Automated tests (D52).

Source of truth

On the docs library, this spec wins over the POC spec and over the 0.8a spec. Where this spec is silent, the 0.8a spec applies.

02

The library

The library has an index page and six pages in four groups. Every page lives under /docs/.

The sidebar shows the four groups in a fixed order. The order follows the reader: first how the app thinks, then how to run a server, then how to build the app, then the project rules.

The page title is the first heading of the Markdown file. The group labels and the index copy are site copy, so they live in apps/site/src/content/en.ts (D43).

One list

The module apps/site/src/lib/docs.ts lists the five Markdown files with their slugs. The content loader, the link plugin and the sidebar read this list. To add a guide, add one line there and one line to the sidebar.

03

Markdown in place

A content loader reads the Markdown files where they are. The build makes no copy (D53).

Starlight reads its pages from a content collection called docs. The collection uses the glob() loader of Astro. Its base is the root of the repository, and its pattern is the five files of lib/docs.ts. A spike on 2026-10-20 (Starlight 0.42.6, Astro 7.4.1) built all five pages this way.

Starlight needs a title in the frontmatter of each page. The files have no frontmatter, and the docs do not add one, because GitHub shows frontmatter as a table on top of the file. A small wrapper around the loader reads the first # heading of the file and gives it as the title. The same wrapper gives the editUrl: the file on GitHub, on main.

The id of each entry is docs/<slug>. Starlight makes the URL from the id, so the page is at /docs/<slug>/.

Caution

Do not add frontmatter to the Markdown files to give Starlight a title. GitHub shows it as a table above the guide. The loader wrapper already gives the title.

04

Links

Links in the Markdown stay relative, so they work on GitHub. A plugin rewrites them for the site at build time (D54).

Astro 7 renders Markdown with Sätteri by default. The remark plugin list of older versions needs another processor. So the site adds one Sätteri mdast plugin, repoLinks, in apps/site/src/lib/repoLinks.ts. It acts only on the five files of lib/docs.ts.

The plugin does two things. It removes the first level-1 heading, because Starlight shows the title as the page h1. It rewrites each link to a .md file, relative to the file that holds the link.

Heading anchors need no change. Astro makes heading ids with the same rules as GitHub, so #letting-people-in points to the same heading in both places.

05

The Guide page

The page /docs/guide/ shows the «Guide» of the app, with the text of the English catalog (D55).

The Guide of the app (0.1) has no Markdown file. Its text is in @saldo/i18n, under guide.*. The site page reads the same keys through appText, as the phone screens of 0.8a do. Thus the catalog is the source of truth for this page.

The list of concepts and sections is in apps/mobile/src/features/guide/concepts.ts today. A package must not import from an app, and the site is an app too. So the list moves to packages/ui/src/guide.ts. @saldo/ui already owns IconName, and the site and the phone both depend on it. The mobile file re-exports the list, so the mobile imports and tests do not change.

The page has one h2 for each section and one h3 for each concept, with its icon, its summary and its body paragraphs. The Starlight contents list shows the sections. The edit link goes to en.ts on GitHub.

The key type of appText comes from the catalog. A concept without a title, a summary or a body in en.ts stops the type check, and a missing key stops the build.

06

Look and theme

The docs pages use the Starlight layout with the colours, radii and fonts of @saldo/ui. The theme choice is the same on the landing page and in the docs (D57).

A Starlight Head override adds the tokensCss() style and the Geist font files of 0.8a. The file apps/site/src/styles/docs.css maps the Starlight variables (--sl-color-*, --sl-font, --sl-font-mono) to the token variables. The site adds no colour.

The site title is the Rocky mark and «Saldo». It links to the landing page. A GitHub icon links to the repository. Every Markdown page has «Edit page» at the end.

Code blocks keep the copy button of Starlight. Their frame uses the token surface and border. The syntax colours use the monochrome themes min-light and min-dark, close to the neutral accent of Saldo.

Starlight has its own theme select and its own storage key. Two overrides replace them. ThemeProvider reads saldo-site-theme before the first paint and sets data-theme to light or dark: Starlight needs one of the two values. ThemeSelect is a toggle with the three states of the landing page: System, Light, Dark.

Caution

Keep the ThemeProvider script inline. A module script runs after the first paint, and the page then flashes from dark to light.

07

Search

Search uses Pagefind, which Starlight includes. The index is static files of the build. No third party gets a query.

After the build, Pagefind reads the HTML of the docs pages and writes dist/pagefind/. The search dialog loads its script and the index only on a docs page, and only when the visitor opens it.

Pagefind indexes the main content of Starlight pages only. The landing page is not in the index. The Guide page is in the index, because it renders inside StarlightPage.

0 hosts

The query stays in the browser. The index is on the same host as the page.

Docs only

The landing page loads no search code. Its budget of 0.8a §07 does not change.

08

Landing page changes

The landing page links to the library. It loads nothing new.

The links move in one module, src/lib/links.ts, as D50 planned. The nav link «Guide» becomes «Docs» and goes to /docs/.

Starlight changes two global options of Astro. It turns on prefetch for all links, which puts a script on the landing page. The spike showed this script. The site sets prefetch: false, so the landing page keeps its three scripts (D46). Starlight also sets scopedStyleStrategy: 'where'. The landing page has no scoped styles, so this changes nothing there.

The sitemap now lists the docs pages. The site uses @astrojs/sitemap, with a filter that leaves out /og/. It writes sitemap-index.xml. The hand-written sitemap.xml.ts goes, and robots.txt names the new file.

Budget

The first load of / stays at most 150 KB gzip (0.8a §07). The plan measures it before and after the change. A docs page has its own target: Lighthouse mobile ≥ 95 in each category.

09

Deploy

The Vercel project of 0.8a does not change. A change to a guide rebuilds the site (D59).

The project has «Skip deployments when there are no changes to the root directory or its dependencies» on. The Markdown files are outside apps/site. The Vercel docs say: «Changes that are not a part of the workspace definition will be considered global changes and deploy all applications in the repository.» docs/ and the files at the root are not in pnpm-workspace.yaml. Thus a change to a guide deploys the site.

Keep apps/site/vercel.json as it is: framework, installCommand, buildCommand, outputDirectory. Do not add an ignoreCommand: git diff HEAD^ HEAD fails on Vercel.

Keep «Include files outside the root directory» on. The loader reads files outside apps/site.

Verify after the merge

Push a commit that changes only a Markdown guide. Make sure that Vercel deploys the site project. If Vercel skips it, set «Skip deployments» to Disabled in Settings → Build and Deployment → Root Directory.

Checks

The site has no automated tests (D52). The type checker, the build and a look at the pages find the errors.

Decisions

The numbers continue from D52. The POC spec lists them with a pointer to this file.

#DecisionReason
D53The docs library is Starlight, inside apps/site. A glob() loader reads the five Markdown files in place. A wrapper gives the title from the first heading and the edit URL.The spike of 2026-10-20 built all five pages with no copy and no frontmatter. Starlight gives the sidebar, the contents list, search, the mobile menu and accessible markup. Own pages would need that code, and the site has no tests.
D54One Sätteri plugin removes the first heading and rewrites relative .md links: to the docs page if the file is in the library, else to GitHub.The links stay relative in the files, so GitHub keeps working. Astro 7 uses Sätteri by default; a remark plugin would need a second Markdown processor.
D55The Guide page renders from guide.* in the English catalog. The list of concepts moves from apps/mobile to @saldo/ui.The Guide has no Markdown file; the catalog is its source. A package must not import from an app, and both the site and the phone depend on @saldo/ui.
D56The library is at /docs/, in English, with four groups. It has no version selector.The landing page keeps /. There are no releases before 0.9, so there is one version to show.
D57The docs pages use the tokens of @saldo/ui and share the theme key saldo-site-theme with the landing page.One site, one look, one choice. AGENTS.md forbids colours outside the palette.
D58prefetch: false. The sitemap comes from @astrojs/sitemap and lists the docs pages.Starlight turns on prefetch for every page, and the landing page would get one more script. Starlight adds @astrojs/sitemap anyway; one sitemap is enough.
D59The Vercel option «Skip deployments» stays on.The Vercel docs count a change outside the workspace packages as a global change. The plan verifies it after the merge, and the fallback is to switch the option off.

12

Open questions

These questions do not stop the plan.

  1. Version selector. When 0.9 has tags, does the library show the guide of each release? Starlight has no built-in versions.
  2. Other languages. The Guide page can read any of the seven catalogs. The Markdown guides are English only. Does a second locale of the site show a translated Guide next to English guides?
  3. The README. Does the library get an «About» page from README.md later?
  4. Starlight versions. Starlight is at 0.x. A minor version can change the component overrides. Check the overrides at each upgrade.
