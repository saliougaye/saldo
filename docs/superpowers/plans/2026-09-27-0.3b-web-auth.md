# 0.3b — Authentication on the web Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** A person opens the instance in a browser, creates an account with a name, an email and a passkey (with an invite code where the server asks for one), or signs in with the passkey their phone already holds; they manage their passkeys and sign out; and a phone whose account still carries the synthetic `{id}@passkey.saldo.invalid` address is asked for a real one.

**Architecture:** The same Better Auth instance, reached with its cookie session instead of the phone's bearer (`authenticate(headers)` is now the one reader, `requireUser` and `currentUser` its two faces). Registration carries an **email** through the passkey plugin's `context` channel, validated and made unique before the ceremony and again when the account row is written; a small Better Auth plugin answers `POST /api/auth/invite/check` so step 2 of `/register` can refuse a bad code **before** a passkey ceremony. The pages are the first web UI: Base UI primitives, CSS Modules over the token variables of 0.3c, strings from `@saldo/i18n` resolved on the server, and every decision they make (which step an error belongs to, which authenticator an AAGUID names, whether a passkey may be deleted) in pure modules with their own tests — the `.tsx` stays thin, because the web's Vitest runs in Node and browser tests are out of 0.3 (§17.1.9).

**Tech Stack:** Next.js 16 (App Router, Server Actions), React 19.2, Better Auth 1.7 (`@better-auth/passkey`), Base UI (`@base-ui/react`), CSS Modules, `geist` (self-hosted font), Zod 4, Vitest with PGlite (web), Jest + React Native Testing Library (mobile).

**Spec:** `docs/superpowers/specs/2026-09-10-saldo-poc-spec.md` §9.1–§9.5, §17.1.1, §17.1.4, §17.1.7 (auth pages, Profilo/passkeys), §18, D26, D32, D34. **Roadmap:** `ROADMAP.md` 0.3b. **Mockup:** `docs/superpowers/mockups/2026-09-27-web-auth-variants.html`, variant «4 · Un passo alla volta» (`#variant=steps`), and `2026-09-27-web-profile-variants.html` for the passkey rows.

## Decisions taken while writing this plan

These fill gaps the spec leaves to the plan, or correct it. Task 21 writes them back into the spec.

1. **`/home` exists in 0.3b as a stub.** §17.1.1 makes `/` redirect to `/home` with a session and to `/login` without one, but Home itself is 0.3d. So `/` gets its final redirect now and `app/(app)/home/page.tsx` is a stub: the account's name and email, a link to the passkeys page and «Esci». 0.3d replaces its body and puts the top bar in `app/(app)/layout.tsx`. Without it, either `/` would need a throwaway redirect target or sign-out would have nowhere to live.
2. **Passkey management lives at `/profile/passkeys` with no Profile shell.** The sub-navigation of Profilo variant «5» belongs to the page that builds Profile (0.3d); 0.3b renders the passkey rows inside the same centred column the auth pages use. The URL is the final one, so 0.3d wraps it rather than moving it.
3. **Web strings are resolved on the server.** `@saldo/i18n` gains `makeTranslator(messages)` — dotted paths, `{{var}}` interpolation, the key itself when it is missing. There is no react-i18next on the web and no catalog in the browser bundle: a client component receives the handful of strings it needs as a typed, plain-object prop. Plurals stay i18next's on the phone; nothing on the web needs one yet.
4. **The locale of a page with no session is `Accept-Language`**; with a session it is `settings.language` through the projection, falling back to `Accept-Language`. That is `resolveLocale` from `@saldo/i18n`, which already answers `en` when it recognises nothing.
5. **Client components hold no testable logic.** The web's Vitest stays `environment: 'node'` with `*.test.ts` only. Step order, error mapping, AAGUID names, email normalisation and the «never the last passkey» rule are pure modules with tests; the components wire them. Adding jsdom and a React renderer to the web app for three forms would buy less than it costs, and browser end-to-end tests are explicitly out (§17.1.9).
6. **The invite check is a Better Auth endpoint**, `POST /api/auth/invite/check`, inside a small `invitePlugin`. A plugin may declare its own `rateLimit` entry (10 per minute per IP), so the check inherits the instance's limiter, its IP resolution and its origin handling instead of growing a second one beside them. It answers `invalid_invite` for unknown, spent, revoked and expired codes alike; `resolveUser` still checks and `afterVerification` still burns, so the endpoint is a convenience and never the gate.
7. **«This email already has an account» is shown on purpose.** It tells a caller which addresses have accounts, which the mockup's step 1 asks for by name. The alternative — one vague refusal — would send somebody who simply forgot they had registered to the admin instead of to `/login`. The disclosure is bounded: the endpoint is rate-limited at 20 per minute per IP, an `invite` or `closed` instance refuses before it answers, and on an `open` instance a caller learns the same thing by trying to register.
8. **A real address is never replaced by 0.3b.** `POST /api/me/email` sets an address **only while the current one is synthetic**; it answers `email_already_set` otherwise. Changing a verified address needs the SMTP of 0.3f.
9. **«In uso ora» comes from this browser, not from the server.** No table links a session to the credential that created it. So the sign-in and add-passkey ceremonies keep the credential id they used in `localStorage` (`saldo.lastPasskeyId`), and the passkeys page marks the row whose `credentialID` matches. It is the honest reading of the spec's «the one that signed **this browser** in», and it costs no column.
10. **Rocky is a static PNG on the web.** The phone's mascot is Lottie (`apps/mobile/assets/mascot/*.json`) and playing it in a browser means a player dependency. `/login` shows `public/rocky/idle.png`, taken from the mockup's own asset. Animating him on the web is a separate, later call.
11. **Geist comes from the `geist` package**, which ships the font files, so a build needs no network and a self-hoster no CDN. `tokensCss()` writes `--font-family: Geist, …`; the root layout appends one line after it, in the same `<style>`, pointing `--font-family` at the package's `--font-geist-sans`. Same specificity, later rule, so it wins without an inline style or a change to `@saldo/ui`.
12. **`afterVerification` must recognise an account that already exists.** With a session, the passkey plugin skips `resolveUser` but still calls `afterVerification` (`resolveRegistrationUser` in the plugin's `index.mjs`). Today's hook would then re-check the registration policy, burn an invite and try to create a user row that is already there — which is exactly what «add a passkey» on `/profile/passkeys` does. The hook returns early when the id already names a user. Nothing exercised this before 0.3b, so it is a latent bug this step fixes.
13. **The CSP now covers the whole app, not only `/auth/**`.** `/login`, `/register`, `/home` and `/profile/**` run the same ceremony and need the same policy; Server Actions need `form-action 'self'`, which is why the app's policy is its own entry and the stricter `/auth/**` one stays as it is.

`packages/i18n/src/translate.ts`:

```ts
import type { Messages } from './locales/it';

export type TranslationVars = Record<string, string | number>;

/** `{{name}}` filled from `vars`; a variable that was not given is left alone, never emptied. */
export function interpolate(template: string, vars: TranslationVars = {}): string {
  return template.replace(/{{(\w+)}}/g, (whole, name: string) =>
    name in vars ? String(vars[name]) : whole,
  );
}

export type Translate = (key: string, vars?: TranslationVars) => string;

/**
 * The `t` of code with no React context: the web's server components and Server Actions (§17.1.7).
 * A missing key answers with itself, so a gap shows up on the page as `web.auth.signInTitle` rather
 * than as an empty element or a crash — and `locales.test.ts` is what stops one being shipped.
 *
 * Plurals are i18next's on the phone (`_one`/`_other`, filled by `withManyPlurals`). Nothing on the
 * web counts anything yet, so this deliberately does not do them: one place to add them later.
 */
export function makeTranslator(messages: Messages): Translate {
  return (key, vars) => {
    let node: unknown = messages;
    for (const part of key.split('.')) {
      if (typeof node !== 'object' || node === null || !(part in node)) return key;
      node = (node as Record<string, unknown>)[part];
    }
    return typeof node === 'string' ? interpolate(node, vars) : key;
  };
}
```

`apps/web/src/i18n/locale.ts`:

```ts
import { type AppLocale, type LanguagePreference, resolveLocale } from '@saldo/i18n';

/**
 * `Accept-Language: it-IT,it;q=0.9,en;q=0.8` → `['it-IT', 'it', 'en']`. Sorted by quality, because
 * a browser may send them in any order, and `q=0` means "not this one" rather than "last".
 */
export function acceptedLanguages(header: string | null): string[] {
  if (header === null) return [];
  return header
    .split(',')
    .map((part) => {
      const [tag = '', ...params] = part.trim().split(';');
      const quality = params.map((param) => param.trim()).find((param) => param.startsWith('q='));
      const weight = quality === undefined ? 1 : Number.parseFloat(quality.slice(2));
      return { tag: tag.trim(), weight: Number.isFinite(weight) ? weight : 0 };
    })
    .filter((entry) => entry.tag.length > 0 && entry.weight > 0)
    .sort((a, b) => b.weight - a.weight)
    .map((entry) => entry.tag);
}

/**
 * The locale a page renders in: the user's `settings.language` when there is one, else the browser's
 * own order. `resolveLocale` is the phone's rule, so the same account reads the same language on
 * both (§17.1.6).
 */
export function webLocale(
  preference: LanguagePreference,
  acceptLanguage: string | null,
): AppLocale {
  return resolveLocale(preference, acceptedLanguages(acceptLanguage));
}
```

```ts
export interface WebI18n {
  locale: AppLocale;
  t: Translate;
}

function forLocale(locale: AppLocale): WebI18n {
  return { locale, t: makeTranslator(catalogs[locale]) };
}
```

```ts
import { and, eq, ne, sql } from 'drizzle-orm';
import { z } from 'zod';
import { user } from '../db/schema';
import type { ServerDatabase } from '../db/types';

/**
 * §9.1 gave passkey-only accounts an address in this domain, before D32 required a real one. RFC
 * 2606 reserves `.invalid`, so it can never route anywhere — which is what makes it safe to treat
 * as "this account has no email yet".
 */
export const SYNTHETIC_EMAIL_DOMAIN = 'passkey.saldo.invalid';

/** The longest address SMTP carries. */
export const MAX_EMAIL_LENGTH = 254;

const schema = z
  .string()
  .trim()
  .max(MAX_EMAIL_LENGTH)
  .transform((value) => value.toLowerCase())
  .pipe(z.email());

/**
 * The stored spelling of what somebody typed, or `null` when it is not an address. Lowercased
 * because the address is an **identifier** (D32) and `Ada@` and `ada@` must not be two accounts.
 */
export function normaliseEmail(input: string): string | null {
  const parsed = schema.safeParse(input);
  return parsed.success ? parsed.data : null;
}

export function syntheticEmail(userId: string): string {
  return `${userId}@${SYNTHETIC_EMAIL_DOMAIN}`;
}

/** Whether this account is still on the pre-D32 placeholder, and so may be given a real address. */
export function isSyntheticEmail(email: string): boolean {
  const at = email.lastIndexOf('@');
  return at !== -1 && email.slice(at + 1).toLowerCase() === SYNTHETIC_EMAIL_DOMAIN;
}

/**
 * Whether some other account already has this address. `lower(email)` rather than a plain compare:
 * rows written before this task exist in whatever case Better Auth was given, and the unique index
 * is on the column, not on its lower case — so this answer and the index can disagree only for
 * those, which is why the index stays the real guard (see `registration.ts`).
 */
export async function emailIsTaken(
  db: ServerDatabase,
  email: string,
  exceptUserId?: string,
): Promise<boolean> {
  const sameAddress = eq(sql`lower(${user.email})`, email.toLowerCase());
  const [row] = await db
    .select({ id: user.id })
    .from(user)
    .where(exceptUserId === undefined ? sameAddress : and(sameAddress, ne(user.id, exceptUserId)))
    .limit(1);
  return row !== undefined;
}
```

```ts
import { APIError } from 'better-auth/api';
import type { ServerDatabase } from '../db/types';
import type { RegistrationMode } from '../env';
import { claimRoleForNewUser } from './admin';
import { emailIsTaken, normaliseEmail } from './email';
import { attributeInvite, burnInvite, inviteIsUsable, releaseInvite } from './invites';
import { registrationAllowed, registrationRequiresInvite } from './policy';
import type { RegistrationContext } from './registrationContext';

/** The half of Better Auth's internal adapter these functions use, injected so they can be tested. */
export interface UserStore {
  findUserById(id: string): Promise<{ id: string; email: string } | null>;
  createUser(input: { id: string; name: string; email: string }): Promise<{ id: string }>;
}

export interface ResolvedRegistration {
  id: string;
  name: string;
  email: string;
}

function refuse(status: 'BAD_REQUEST' | 'FORBIDDEN' | 'CONFLICT', code: string, message: string) {
  return new APIError(status, { code, message });
}

/**
 * The passkey plugin's `resolveUser`: it runs **before** the ceremony, decides the WebAuthn user
 * handle, and is where the registration policy is enforced. No row is written here — the account is
 * created in `completeRegistration` — so a ceremony the user abandons leaves nothing behind, and the
 * invite is only *checked*, never spent, for the same reason.
 */
export async function resolveRegistration(
  db: ServerDatabase,
  options: { mode: RegistrationMode; context: RegistrationContext; now: Date },
): Promise<ResolvedRegistration> {
  const { mode, context, now } = options;
  if (!(await registrationAllowed(db, mode))) {
    throw refuse('FORBIDDEN', 'registration_closed', 'This server is not accepting new accounts');
  }
  if (context.name.length === 0) {
    throw refuse('BAD_REQUEST', 'display_name_required', 'Choose a name first');
  }
  const email = normaliseEmail(context.email);
  if (email === null) {
    throw refuse('BAD_REQUEST', 'email_required', 'Enter a valid email address');
  }
  // D32: an identifier, not a credential — and one account per address, so this is checked before
  // the ceremony rather than after it. The answer tells a caller which addresses have accounts; see
  // decision 7 in the plan for why that is the chosen trade.
  if (await emailIsTaken(db, email)) {
    throw refuse('CONFLICT', 'email_taken', 'That email already has an account');
  }
  if (registrationRequiresInvite(mode) && !(await inviteIsUsable(db, context.invite ?? '', now))) {
    // One answer for unknown, spent, revoked and expired: the form must not be usable to find out
    // which codes exist.
    throw refuse('FORBIDDEN', 'invalid_invite', 'That invite code is not valid');
  }
  return { id: crypto.randomUUID(), name: context.name, email };
}

/**
 * The passkey plugin's `afterVerification`: the plugin never creates users — it needs a `userId` to
 * name one that already exists — so the account is written here, with the id the ceremony used as
 * its handle.
 *
 * **When there is a session, the plugin skips `resolveUser` and still calls this** (its
 * `resolveRegistrationUser`), which is what «add a passkey» from Profile does. So an id that already
 * names an account means "another passkey for this account": nothing to create, no policy to apply,
 * no invite to spend.
 */
export async function completeRegistration(
  db: ServerDatabase,
  options: {
    mode: RegistrationMode;
    context: RegistrationContext;
    resolved: { id: string; name: string };
    store: UserStore;
    now: Date;
  },
): Promise<{ userId: string }> {
  const { mode, context, resolved, store, now } = options;
  const existing = await store.findUserById(resolved.id);
  if (existing !== null) return { userId: existing.id };

  if (!(await registrationAllowed(db, mode))) {
    throw refuse('FORBIDDEN', 'registration_closed', 'This server is not accepting new accounts');
  }
  const email = normaliseEmail(context.email);
  if (email === null) {
    throw refuse('BAD_REQUEST', 'email_required', 'Enter a valid email address');
  }

  /**
   * Spend the code **before** writing the account. Two ceremonies holding the same code reach this
   * line together; the burn is a conditional UPDATE, so exactly one of them gets an id and the other
   * is refused. The other way round would create both accounts and then refuse one, leaving an orphan.
   */
  let burnedInviteId: string | null = null;
  if (registrationRequiresInvite(mode)) {
    burnedInviteId = await burnInvite(db, context.invite ?? '', now);
    if (burnedInviteId === null) {
      throw refuse('FORBIDDEN', 'invalid_invite', 'That invite code is not valid');
    }
  }

  try {
    const created = await store.createUser({ id: resolved.id, name: resolved.name, email });
    /**
     * §9.5: the first account on the instance is the admin, and under `invite` it can only exist
     * because somebody with shell access minted its code. Every later one is a member. This runs
     * **after** the row exists, because the claim is decided by "is the earliest account mine"
     * rather than by the table being empty — see `claimRoleForNewUser`, which takes a lock so two
     * ceremonies finishing together cannot both win, and cannot both lose either.
     */
    await claimRoleForNewUser(db, created.id);
    // Now that the row exists, the invite can say whose it was. Last, and on purpose: `used_by`
    // points at `user`, and it is a record rather than a decision.
    if (burnedInviteId !== null) await attributeInvite(db, burnedInviteId, created.id);
    return { userId: created.id };
  } catch (error) {
    // The account was not created, so the code was not really used: give it back rather than leave
    // the person holding one that never worked.
    if (burnedInviteId !== null) await releaseInvite(db, burnedInviteId);
    // The unique index on `email` is the real guard against two accounts on one address — the check
    // in `resolveRegistration` can be overtaken by a ceremony that started a moment earlier. When
    // that is what happened, say so in the words the form knows.
    if (await emailIsTaken(db, email)) {
      throw refuse('CONFLICT', 'email_taken', 'That email already has an account');
    }
    throw error;
  }
}
```

```ts
import { isRevoked } from './admin';
import { auth } from './auth';
import { getDb } from '../db/client';

export interface AuthenticatedUser {
  id: string;
  displayName: string;
  /** Synthetic (`@passkey.saldo.invalid`) for an account created before D32; see `email.ts`. */
  email: string;
  emailVerified: boolean;
}

/**
 * The one place a session is read. The `bearer` plugin lets `getSession` take the token out of the
 * Authorization header, and a browser's cookie arrives in the same headers — so the phone's bearer
 * and the web's cookie session are literally one call (§17.1.4).
 *
 * The revocation check is ours and is deliberately not left to the library: better-auth only tests
 * the ban flag when a session is **created**, so a live token would otherwise survive until its
 * session row happened to be deleted. §10 promises a revoked account stops at once, and that promise
 * is kept here rather than by remembering to delete rows everywhere else.
 */
export async function authenticate(headers: Headers): Promise<AuthenticatedUser | null> {
  const session = await auth().api.getSession({ headers });
  if (session === null) return null;
  if (await isRevoked(getDb(), session.user.id)) return null;
  return {
    id: session.user.id,
    displayName: session.user.name,
    email: session.user.email,
    emailVerified: session.user.emailVerified,
  };
}
```

```ts
import { eq } from 'drizzle-orm';
import { z } from 'zod';
import {
  emailIsTaken,
  isSyntheticEmail,
  MAX_EMAIL_LENGTH,
  normaliseEmail,
} from '../../../../src/server/auth/email';
import { getDb } from '../../../../src/server/db/client';
import { user } from '../../../../src/server/db/schema';
import { ApiError, handle } from '../../../../src/server/http/errors';
import { readJson } from '../../../../src/server/http/json';
import { requireUser } from '../../../../src/server/http/requireUser';

export const runtime = 'nodejs';
export const dynamic = 'force-dynamic';

const schema = z.object({ email: z.string().max(MAX_EMAIL_LENGTH) });

/**
 * D32: every account carries an email. An account created before that has the synthetic address of
 * §9.1, and this is how it gets a real one — from the phone's onboarding or its server screen
 * (§17.1.4), and later from Profile on the web.
 *
 * It only ever fills an empty seat: replacing a real address means proving the new one belongs to the
 * person, and there is no SMTP until 0.3f. So the answer to "change my email" is 409 until then.
 */
export function POST(request: Request): Promise<Response> {
  return handle(async () => {
    const account = await requireUser(request);
    const body = await readJson(request, schema);
    const email = normaliseEmail(body.email);
    if (email === null) {
      throw new ApiError(400, 'invalid_email', 'That is not an email address');
    }
    if (!isSyntheticEmail(account.email)) {
      throw new ApiError(
        409,
        'email_already_set',
        'This account already has an email address',
      );
    }
    const db = getDb();
    if (await emailIsTaken(db, email, account.id)) {
      throw new ApiError(409, 'email_taken', 'That email already has an account');
    }
    // `emailVerified` stays false: nothing has proved the mailbox is theirs, and until SMTP exists
    // (0.3f) nothing can. The column is the record of that, not a formality.
    await db.update(user).set({ email, emailVerified: false }).where(eq(user.id, account.id));
    return Response.json({ email, emailVerified: false });
  });
}
```

`apps/web/src/server/auth/invitePlugin.ts`:

```ts
import type { BetterAuthPlugin } from 'better-auth';
import { APIError, createAuthEndpoint } from 'better-auth/api';
import { z } from 'zod';
import { getDb } from '../db/client';
import type { RegistrationMode } from '../env';
import { inviteIsUsable } from './invites';
import { registrationRequiresInvite } from './policy';

/** Tighter than the instance's 20/minute: a code is 80 random bits, so guessing is hopeless anyway,
 * and the only reason to call this in a loop is to find out which codes exist. */
const WINDOW_SECONDS = 60;
const MAX_PER_WINDOW = 10;

/** The longest thing worth parsing as a code: 16 symbols, dashes, and a generous margin for spaces. */
const MAX_CODE_LENGTH = 64;

/**
 * `POST /api/auth/invite/check` (§17.1.7, auth pages). It exists so step 2 of `/register` can refuse a
 * bad code **before** the passkey ceremony. It is a convenience and never the gate: `resolveUser`
 * checks the code again and `completeRegistration` is what spends it, so a caller that skips this
 * endpoint gains nothing.
 *
 * It is a Better Auth endpoint rather than a route of our own so that it sits behind the same rate
 * limiter, the same trusted-proxy IP resolution and the same origin handling as `/sign-in*` — one
 * limiter for the instance, not two with different ideas of who the caller is.
 */
export function invitePlugin(mode: RegistrationMode) {
  return {
    id: 'saldo-invite',
    endpoints: {
      checkInvite: createAuthEndpoint(
        '/invite/check',
        { method: 'POST', body: z.object({ invite: z.string().max(MAX_CODE_LENGTH) }) },
        async (ctx) => {
          // Nothing to check on a server that does not ask for a code: the form never shows the step.
          if (!registrationRequiresInvite(mode)) return ctx.json({ valid: true });
          if (!(await inviteIsUsable(getDb(), ctx.body.invite, new Date()))) {
            // One answer for unknown, spent, revoked and expired — the same one `resolveUser` gives.
            throw new APIError('FORBIDDEN', {
              code: 'invalid_invite',
              message: 'That invite code is not valid',
            });
          }
          return ctx.json({ valid: true });
        },
      ),
    },
    rateLimit: [
      { pathMatcher: (path: string) => path === '/invite/check', window: WINDOW_SECONDS, max: MAX_PER_WINDOW },
    ],
  } satisfies BetterAuthPlugin;
}
```

`inviteIsUsable` hashes through `normaliseInviteCode`, which is why a lower-case code with spaces in it
is the same code — the test above pins that.

```ts
/** §17.1.7, auth pages: one decision per screen, the invite only where the server asks for one. */
export type RegisterStep = 'identity' | 'invite' | 'passkey';

export function registerSteps(requiresInvite: boolean): RegisterStep[] {
  return requiresInvite ? ['identity', 'invite', 'passkey'] : ['identity', 'passkey'];
}

export function stepAfter(steps: readonly RegisterStep[], current: RegisterStep): RegisterStep | null {
  return steps[steps.indexOf(current) + 1] ?? null;
}

export function stepBefore(
  steps: readonly RegisterStep[],
  current: RegisterStep,
): RegisterStep | null {
  const index = steps.indexOf(current);
  return index <= 0 ? null : steps[index - 1] ?? null;
}

/** Which field caused a refusal, by the code the server sent. */
const OWNER: Record<string, RegisterStep> = {
  email_taken: 'identity',
  email_required: 'identity',
  display_name_required: 'identity',
  invalid_invite: 'invite',
};

/**
 * «Ogni errore sta nel passo dove nasce» (§17.1.7). Anything the steps did not cause — a closed
 * server, a cancelled ceremony, a rate limit — belongs where the ceremony runs, which is the last step.
 */
export function stepForErrorCode(
  code: string | undefined,
  steps: readonly RegisterStep[],
): RegisterStep {
  const owner = code === undefined ? undefined : OWNER[code];
  if (owner !== undefined && steps.includes(owner)) return owner;
  if (owner !== undefined) return steps[0] ?? 'identity';
  return steps[steps.length - 1] ?? 'passkey';
}
```

```ts
export interface AuthMessage {
  titleKey: string;
  bodyKey: string;
}

/** What the browser and `@simplewebauthn` call "the person closed the window". */
const CANCELLED = new Set([
  'AUTH_CANCELLED',
  'ERROR_CEREMONY_ABORTED',
  'REGISTRATION_CANCELLED',
  'NotAllowedError',
]);

const BY_CODE: Record<string, AuthMessage> = {
  email_taken: { titleKey: 'web.auth.emailTakenTitle', bodyKey: 'web.auth.emailTakenBody' },
  email_required: { titleKey: 'web.auth.emailInvalid', bodyKey: 'web.auth.emailHint' },
  invalid_invite: {
    titleKey: 'web.auth.invalidInviteTitle',
    bodyKey: 'web.auth.invalidInviteBody',
  },
  registration_closed: { titleKey: 'web.auth.closedTitle', bodyKey: 'web.auth.closedBody' },
  display_name_required: { titleKey: 'web.auth.emailInvalid', bodyKey: 'web.auth.emailHint' },
};

/**
 * The two i18n keys an error becomes. Deliberately not the server's `message`: it is English, written
 * for a log, and the page has seven languages. An unrecognised code is one sentence and the hint that
 * covers the commonest real cause — a browser with no passkey on it.
 */
export function describeAuthError(code: string | undefined): AuthMessage {
  if (code !== undefined && CANCELLED.has(code)) {
    return { titleKey: 'sync.cancelled', bodyKey: 'web.auth.cancelledBody' };
  }
  return (
    (code === undefined ? undefined : BY_CODE[code]) ?? {
      titleKey: 'web.auth.genericError',
      bodyKey: 'web.auth.crossDeviceHint',
    }
  );
}
```

```ts
const KEY = 'saldo.lastPasskeyId';

interface Storage {
  getItem(key: string): string | null;
  setItem(key: string, value: string): void;
}

function browserStorage(): Storage | null {
  // Server-rendered, or a browser that refuses storage in a private window: both mean "do not know".
  if (typeof window === 'undefined') return null;
  try {
    return window.localStorage;
  } catch {
    return null;
  }
}

/**
 * Decision 9: no table links a session to the credential that created it, so the ceremony that
 * signed **this browser** in says which one it used, here. Losing it costs one «in uso ora» label.
 */
export function rememberPasskey(credentialId: string, storage: Storage | null = browserStorage()) {
  try {
    storage?.setItem(KEY, credentialId);
  } catch {
    // A full or refused storage is not worth a failed sign-in.
  }
}

export function lastPasskeyId(storage: Storage | null = browserStorage()): string | null {
  try {
    return storage?.getItem(KEY) ?? null;
  } catch {
    return null;
  }
}
```

```tsx
'use client';

import { useRouter } from 'next/navigation';
import { useEffect, useRef, useState } from 'react';
import { authClient } from '../../../src/client/authClient';
import { log } from '../../../src/client/log';
import { describeAuthError } from '../../../src/features/auth/authErrors';
import { rememberPasskey } from '../../../src/features/auth/lastPasskey';
import { Alert } from '../../../src/ui/Alert';
import { Button } from '../../../src/ui/Button';
import { TextField } from '../../../src/ui/TextField';
import styles from '../auth.module.css';

export interface LoginStrings {
  emailLabel: string;
  emailPlaceholder: string;
  signIn: string;
  working: string;
  crossDeviceHint: string;
  cancelledTitle: string;
  cancelledBody: string;
  genericTitle: string;
  genericBody: string;
}

/**
 * The passkey ceremony, twice over: armed for the browser's **conditional UI** as soon as the page
 * loads — which is what makes the email field offer the passkey when it is focused, together with
 * `autocomplete="username webauthn"` — and run outright by the button.
 *
 * `@simplewebauthn/browser` aborts any ceremony in flight when a new one starts, so pressing the
 * button while autofill is armed is safe; the armed one then fails with an abort, which is ignored.
 */
export function LoginForm({ strings }: { strings: LoginStrings }) {
  const router = useRouter();
  const [busy, setBusy] = useState(false);
  const [error, setError] = useState<{ title: string; body: string } | null>(null);
  const armed = useRef(false);

  const succeed = (credentialId: string | undefined) => {
    if (credentialId !== undefined) rememberPasskey(credentialId);
    // `replace`: the sign-in page must not come back on a hardware back from inside the app.
    router.replace('/home');
  };

  useEffect(() => {
    if (armed.current) return;
    armed.current = true;
    void (async () => {
      log('auth', 'arming the browser’s passkey autofill');
      const { data, error: failure } = await authClient.signIn.passkey({
        autoFill: true,
        returnWebAuthnResponse: true,
      });
      // An abort is the button taking over, and a browser with no conditional UI simply never
      // resolves this — neither is worth a word on screen.
      if (failure !== null || data === null) return;
      succeed(data.webauthn?.response.id);
    })();
    // The ceremony is armed once per page, not once per render.
    // eslint-disable-next-line react-hooks/exhaustive-deps
  }, []);

  const signIn = async () => {
    setBusy(true);
    setError(null);
    const { data, error: failure } = await authClient.signIn.passkey({
      returnWebAuthnResponse: true,
    });
    if (failure !== null || data === null) {
      const code = failure === null ? undefined : 'code' in failure ? failure.code : undefined;
      log('auth', 'the passkey ceremony failed', { status: failure?.status, code });
      const message = describeAuthError(typeof code === 'string' ? code : undefined);
      setError(
        message.titleKey === 'sync.cancelled'
          ? { title: strings.cancelledTitle, body: strings.cancelledBody }
          : { title: strings.genericTitle, body: strings.genericBody },
      );
      setBusy(false);
      return;
    }
    succeed(data.webauthn?.response.id);
  };

  return (
    <>
      {error === null ? null : <Alert title={error.title} body={error.body} />}
      <div className={styles.fields}>
        <TextField
          label={strings.emailLabel}
          placeholder={strings.emailPlaceholder}
          type="email"
          name="email"
          /** What makes the browser offer the passkey the moment this field is touched. */
          autoComplete="username webauthn"
          autoCapitalize="none"
          spellCheck={false}
        />
      </div>
      <Button icon="key" busy={busy} busyLabel={strings.working} onClick={() => void signIn()}>
        {strings.signIn}
      </Button>
      <p className={`${styles.hint} ${styles.centred}`}>{strings.crossDeviceHint}</p>
    </>
  );
}
```

The email field is **not** sent anywhere: sign-in is by discoverable credential (§9.3, `residentKey:
'required'`), so the server never learns an identifier from this page. The field exists because it is
what triggers the browser's passkey autofill; that is why it has no `value`/`onChange`.

```tsx
import { useRouter } from 'next/navigation';
import { useState } from 'react';
import { authClient } from '../../../src/client/authClient';
import { log } from '../../../src/client/log';
import { describeAuthError } from '../../../src/features/auth/authErrors';
import { rememberPasskey } from '../../../src/features/auth/lastPasskey';
import { registrationContextJson } from '../../../src/features/auth/registrationBody';
import {
  type RegisterStep,
  registerSteps,
  stepBefore,
  stepForErrorCode,
} from '../../../src/features/auth/registerSteps';
import type { InstanceInfo } from '../../../src/server/instance';
import { Alert } from '../../../src/ui/Alert';
import { AuthFooter, Brand } from '../../../src/ui/Brand';
import { Button } from '../../../src/ui/Button';

import { Steps, stepsBackClass } from '../../../src/ui/Steps';
import { TextField } from '../../../src/ui/TextField';
import styles from '../auth.module.css';

/** Every string this flow can show, resolved by the page. Keys that name an i18n path are the ones
 * `describeAuthError` answers with. */
export type RegisterStrings = Record<string, string>;

interface Props {
  requiresInvite: boolean;
  initialInvite: string;
  instance: InstanceInfo;
  strings: RegisterStrings;
  stepLabels: string[];
}

/** An error, and the step it belongs in. */
interface Refusal {
  step: RegisterStep;
  title: string;
  body: string;
}

export function RegisterFlow({
  requiresInvite,
  initialInvite,
  instance,
  strings,
  stepLabels,
}: Props) {
  const router = useRouter();
  const steps = registerSteps(requiresInvite);
  const [step, setStep] = useState<RegisterStep>('identity');
  const [name, setName] = useState('');
  const [email, setEmail] = useState('');
  const [invite, setInvite] = useState(initialInvite);
  const [busy, setBusy] = useState(false);
  const [refusal, setRefusal] = useState<Refusal | null>(null);

  const at = steps.indexOf(step) + 1;
  const shown = refusal !== null && refusal.step === step ? refusal : null;
  const refuse = (code: string | undefined) => {
    const message = describeAuthError(code);
    setRefusal({
      step: stepForErrorCode(code, steps),
      title: strings[message.titleKey] ?? strings['web.auth.genericError'] ?? '',
      body: strings[message.bodyKey] ?? '',
    });
    setStep(stepForErrorCode(code, steps));
  };

  /** Step 1 → 2 (or straight to the ceremony when the server asks for no code). */
  const submitIdentity = () => {
    setRefusal(null);
    // The server validates it too (`normaliseEmail`); this is so the person is not sent to the next
    // screen only to be turned back.
    if (name.trim().length === 0 || !email.includes('@')) {
      refuse('email_required');
      return;
    }
    setStep(requiresInvite ? 'invite' : 'passkey');
  };

  /**
   * Step 2. §17.1.7: the code is checked **here**, before the ceremony, so nobody puts a finger on a
   * sensor to be told afterwards that it was wrong. The check is a convenience — `resolveUser` checks
   * again and the registration is what spends the code.

  const submitInvite = async () => {
```

```tsx
  registerSteps,
  stepBefore,
  stepForErrorCode,
} from '../../../src/features/auth/registerSteps';
import type { InstanceInfo } from '../../../src/server/instance';
import { Alert } from '../../../src/ui/Alert';
import { Brand } from '../../../src/ui/Brand';
import { Button } from '../../../src/ui/Button';
import { Icon } from '../../../src/ui/Icon';
import { Steps, stepsBackClass } from '../../../src/ui/Steps';
import { TextField } from '../../../src/ui/TextField';
import styles from '../../(auth)/auth.module.css';

interface Props {
  redirectUri: string;
  state: string;
  canRegister: boolean;
  requiresInvite: boolean;
  initialMode: 'login' | 'register';
  instance: InstanceInfo;
  strings: Record<string, string>;
  stepLabels: string[];
}

/**
 * §9.3 steps 4–5. The ceremony runs here because the app has no `navigator.credentials`; on success a
 * one-time token is minted and travels back in the deep link, single use, one minute, stored hashed.
 * The app cannot read this browser's cookie, which is the whole reason the token exists.
 */
export function MobileAuth({
  redirectUri,
  state,
  canRegister,
  requiresInvite,
  initialMode,
  instance,
  strings,
  stepLabels,
}: Props) {
  const steps = registerSteps(requiresInvite);
  const [mode, setMode] = useState<'login' | 'register'>(initialMode);
  const [step, setStep] = useState<RegisterStep>('identity');
  const [name, setName] = useState('');
  const [email, setEmail] = useState('');
  const [invite, setInvite] = useState('');
  const [busy, setBusy] = useState(false);
  const [handedOff, setHandedOff] = useState(false);
  const [refusal, setRefusal] = useState<{ step: RegisterStep; title: string; body: string } | null>(
    null,
  );

  /**
   * The two lines that explain most failed ceremonies before anything is clicked: WebAuthn needs a
   * secure context, and a browser without a platform authenticator cannot run it at all. Both look
   * like "the button does nothing" from the phone.
   */
  useEffect(() => {
    log('auth', 'the sign-in page is ready', {
      mode: initialMode,
      canRegister,
      requiresInvite,
      redirectScheme: redirectUri.split(':')[0],
      secureContext: window.isSecureContext,
      webauthn: typeof window.PublicKeyCredential !== 'undefined',
      origin: window.location.origin,
    });
  }, [initialMode, canRegister, requiresInvite, redirectUri]);

  const refuse = (code: string | undefined) => {
    const message = describeAuthError(code);
    const owner = stepForErrorCode(code, steps);
    setRefusal({
      step: owner,
      title: strings[message.titleKey] ?? strings['web.auth.genericError'] ?? '',
      body: strings[message.bodyKey] ?? '',
    });
    setStep(owner);
    setBusy(false);
  };

  /** The ceremony left this browser holding a session; the app gets a one-time token instead. */
  const handOff = async () => {
    log('auth', 'the ceremony left a session here, minting the handoff token');
    const { data, error } = await authClient.oneTimeToken.generate();
    if (error !== null || data === null) {
      log('auth', 'the server would not mint a handoff token', {
        status: error?.status,
        message: error?.message,
      });
      refuse(undefined);
      return;
    }
    const url = new URL(redirectUri);
    url.searchParams.set('ott', data.token);
    url.searchParams.set('state', state);
    // The scheme only. The whole point of the token is that nothing but the app ever reads it, and a
    // console is somewhere it would be readable.
    log('auth', `handing back to ${url.protocol}//${url.host}${url.pathname}`);
    setHandedOff(true);
    window.location.href = url.toString();
  };

  const signIn = async () => {
    setRefusal(null);
    setBusy(true);
    log('auth', 'asking the browser for a passkey');
    const { error } = await authClient.signIn.passkey();
    if (error !== null) {
      const code = 'code' in error ? error.code : undefined;
      log('auth', 'the passkey ceremony failed', { status: error.status, code });
      refuse(typeof code === 'string' ? code : undefined);
      return;
    }
    await handOff();
  };

  const submitIdentity = () => {
    setRefusal(null);
    if (name.trim().length === 0 || !email.includes('@')) {
      refuse('email_required');
      return;
    }
    setStep(requiresInvite ? 'invite' : 'passkey');
  };

  const submitInvite = async () => {
    setRefusal(null);
    setBusy(true);
    const { error } = await authClient.$fetch<{ valid: boolean }>('/invite/check', {
      method: 'POST',
      body: { invite },
    });
    setBusy(false);
    if (error !== null) {
      refuse('invalid_invite');
      return;
    }
    setStep('passkey');
  };

  const createPasskey = async () => {
    setRefusal(null);
    setBusy(true);
    log('auth', 'creating a passkey for a new account', { withInvite: requiresInvite });
    const { error } = await authClient.passkey.addPasskey({
      context: registrationContextJson({
        name: name.trim(),
        email: email.trim(),
        invite: requiresInvite ? invite : null,
      }),
      createSession: true,
    });
    if (error !== null) {
      const code = 'code' in error ? error.code : undefined;
      log('auth', 'the server refused the registration', { status: error.status, code });
      refuse(typeof code === 'string' ? code : undefined);
      return;
    }
    await handOff();
  };

  if (handedOff) {
    return (
      <div className={styles.done}>
        <span className={styles.check}>
          <Icon name="check" size={26} />
        </span>
        <h1 className={styles.title}>{strings.doneTitle}</h1>
        <p className={styles.lede}>{strings.doneBody}</p>
      </div>
    );
  }

  const shown = refusal !== null && refusal.step === step ? refusal : null;

  if (mode === 'login') {
    return (
      <>
        <Brand instanceName={instance.name} />
        <h1 className={styles.title}>{strings.signInTitle}</h1>
        <p className={styles.lede}>{strings.signInBody}</p>
        {refusal === null ? null : <Alert title={refusal.title} body={refusal.body} />}
        <Button icon="key" busy={busy} busyLabel={strings.working} onClick={() => void signIn()}>
          {strings.signIn}
        </Button>
        {canRegister ? (
          <>
            <div className={styles.or}>{strings.or ?? ''}</div>
            <Button
              variant="secondary"
              disabled={busy}
              onClick={() => {
                setRefusal(null);
                setStep('identity');
                setMode('register');
              }}
            >
              {strings.createAccount}
            </Button>
          </>
        ) : null}
      </>
    );
  }

  const at = steps.indexOf(step) + 1;
  return (
    <>
      {at > 1 ? (
        <button
          type="button"
          className={stepsBackClass}
          onClick={() => {
            setRefusal(null);
            const previous = stepBefore(steps, step);
            if (previous === null) setMode('login');
            else setStep(previous);
          }}
        >
          <Icon name="chevL" size={14} />
          {strings.back}
        </button>
      ) : (
        <Brand instanceName={instance.name} />
      )}
      <Steps at={at} total={steps.length} label={stepLabels[at - 1] ?? ''} />

      {step === 'identity' ? (
        <>
          <h1 className={styles.title}>{strings.registerTitle}</h1>
          <p className={styles.lede}>{strings.registerBody}</p>
          {shown === null ? null : <Alert title={shown.title} body={shown.body} />}
          <div className={styles.fields}>
            <TextField
              label={strings.nameLabel}
              value={name}
              onChange={(event) => setName(event.target.value)}
              autoComplete="name"
              maxLength={80}
            />
            <TextField
              label={strings.emailLabel}
              placeholder={strings.emailPlaceholder}
              hint={strings.emailHint}
              value={email}
              onChange={(event) => setEmail(event.target.value)}
              type="email"
              autoComplete="email"
              autoCapitalize="none"
              spellCheck={false}
              invalid={shown !== null}
            />
          </div>
          <Button onClick={submitIdentity}>{strings.continue}</Button>
          <p className={styles.switchLine}>
            {strings.haveAccount}{' '}
            <button
              type="button"
              onClick={() => {
                setRefusal(null);
                setMode('login');
              }}
            >
              {strings.signInLink}
            </button>
          </p>
        </>
      ) : null}

      {step === 'invite' ? (

            hint={strings.inviteHint}

            mono
```

```ts
export interface StoredPasskey {
  id: string;
  name: string | null;
  credentialId: string;
  aaguid: string | null;
  /** Better Auth's `backed_up`: the authenticator syncs this credential to its own cloud. */
  backedUp: boolean;
  /** ISO 8601, or null for a row Better Auth wrote without one. */
  createdAt: string | null;
}

/** Decision 9: `inUse` is the credential this browser's last ceremony used. */
export type PasskeyRow<T extends StoredPasskey = StoredPasskey> = T & { inUse: boolean };

/**
 * Newest first, undated last, with «in uso ora» on the credential this browser signed in with.
 * Generic so that whatever the page has already added to a row — the formatted «Aggiunta il …» —
 * survives the sort in the type as well as at run time.
 */
export function passkeyRows<T extends StoredPasskey>(
  passkeys: readonly T[],
  lastCredentialId: string | null,
): PasskeyRow<T>[] {
  return [...passkeys]
    .sort((a, b) => {
      if (a.createdAt === null) return b.createdAt === null ? 0 : 1;
      if (b.createdAt === null) return -1;
      return b.createdAt.localeCompare(a.createdAt);
    })
    .map((passkey) => ({
      ...passkey,
      inUse: lastCredentialId !== null && passkey.credentialId === lastCredentialId,
    }));
}

/**
 * §17.1.7: never the last one. Deleting it would lock the account out of every device at once, and
 * there is no recovery until SMTP exists (0.3f). The button says why; the Server Action refuses too.
 */
export function canDeletePasskey(total: number): boolean {
  return total > 1;
}
```

```ts
import { eq } from 'drizzle-orm';
import type { StoredPasskey } from '../../features/passkeys/list';
import { passkey } from '../db/schema';
import type { ServerDatabase } from '../db/types';

/**
 * The passkeys of one account, for `/profile/passkeys`. Read straight from the table rather than
 * through `auth.api.listPasskeys` because a Server Component wants typed rows and no public key: the
 * page shows a name, an authenticator and a date, and nothing here should ever reach a browser that
 * the page does not draw.
 */
export async function listPasskeysForUser(
  db: ServerDatabase,
  userId: string,
): Promise<StoredPasskey[]> {
  const rows = await db
    .select({
      id: passkey.id,
      name: passkey.name,
      credentialId: passkey.credentialID,
      aaguid: passkey.aaguid,
      backedUp: passkey.backedUp,
      createdAt: passkey.createdAt,
    })
    .from(passkey)
    .where(eq(passkey.userId, userId));
  return rows.map((row) => ({
    id: row.id,
    name: row.name,
    credentialId: row.credentialId,
    aaguid: row.aaguid,
    backedUp: row.backedUp,
    createdAt: row.createdAt === null ? null : row.createdAt.toISOString(),
  }));
}
```

```ts
import { headers } from 'next/headers';
import { revalidatePath } from 'next/cache';
import { canDeletePasskey } from '../../../../src/features/passkeys/list';
import { auth } from '../../../../src/server/auth/auth';
import { requireWebUser } from '../../../../src/server/auth/currentUser';
import { listPasskeysForUser } from '../../../../src/server/auth/passkeys';
import { getDb } from '../../../../src/server/db/client';
import { log } from '../../../../src/server/log';

/** What the client does with the answer: show nothing, or one line where the row is. */
export type PasskeyActionResult = { ok: true } | { ok: false; reason: 'last_one' | 'failed' };

const MAX_NAME_LENGTH = 60;

/**
 * §17.1.7: the name is Saldo's own label — the authenticator's name does not change — so this is a
 * plain rename, and an empty one puts the row back to «Passkey».
 */
export async function renamePasskeyAction(
  id: string,
  name: string,
): Promise<PasskeyActionResult> {
  const user = await requireWebUser();
  const trimmed = name.trim().slice(0, MAX_NAME_LENGTH);
  try {
    // The endpoint checks the passkey belongs to the session (`requireResourceOwnership`), so an id
    // from somewhere else is refused there rather than trusted here.
    await auth().api.updatePasskey({ body: { id, name: trimmed }, headers: await headers() });
  } catch (error) {
    log('auth', 'renaming a passkey failed', { user: user.id, error: String(error) });
    return { ok: false, reason: 'failed' };
  }
  revalidatePath('/profile/passkeys');
  return { ok: true };
}

/**
 * Never the last one. The rule lives here and not only in the button: a disabled button is a
 * courtesy, and this is the promise (§17.1.7).
 */
export async function deletePasskeyAction(id: string): Promise<PasskeyActionResult> {
  const user = await requireWebUser();
  const existing = await listPasskeysForUser(getDb(), user.id);
  if (!canDeletePasskey(existing.length)) return { ok: false, reason: 'last_one' };
  try {
    await auth().api.deletePasskey({ body: { id }, headers: await headers() });
  } catch (error) {
    log('auth', 'deleting a passkey failed', { user: user.id, error: String(error) });
    return { ok: false, reason: 'failed' };
  }
  revalidatePath('/profile/passkeys');
  return { ok: true };
}
```

```ts
import type { SignedInUser } from '../../auth/session';

/**
 * §9.1's placeholder domain, in the reserved `.invalid` TLD. The web knows it as
 * `SYNTHETIC_EMAIL_DOMAIN`; the phone cannot import from `apps/web`, so the constant is written twice
 * — and changing it would be a server migration anyway, not a rename.
 */
const SYNTHETIC_DOMAIN = 'passkey.saldo.invalid';

/**
 * Whether this account still has no real address (D32). The phone then asks for one, in onboarding and
 * on the server screen, which is how an account created before 0.3b gets one.
 */
export function needsEmail(user: SignedInUser | null): boolean {
  if (user === null) return false;
  const at = user.email.lastIndexOf('@');
  return at !== -1 && user.email.slice(at + 1).toLowerCase() === SYNTHETIC_DOMAIN;
}

/**
 * Enough to know the field is worth sending: `POST /api/me/email` is what actually decides, with the
 * same rule for every client. This only spares the person a round trip.
 */
export function emailLooksValid(input: string): boolean {
  const value = input.trim();
  return /^[^\s@]+@[^\s@.]+(\.[^\s@.]+)+$/.test(value) && value.length <= 254;
}
```

```tsx
import { View } from 'react-native';
import { PrimaryButton, SecondaryButton } from '../../components/Button';
import { ConfirmDialog } from '../../components/ConfirmDialog';
import { TextField } from '../../components/TextField';
import { Text } from '../../theme/Text';
import { emailLooksValid } from './emailAsk';

interface Props {
  visible: boolean;
  /** Rejects with an `ApiClientError`; `email_taken` is the one the field itself can answer. */
  onSave: (email: string) => Promise<void>;
  onDismiss: () => void;
}

/**
 * D32: every account carries an email. An account created before 0.3b has the synthetic address of
 * §9.1, and this is where it gets a real one — after a sign-in, and from the server screen for anybody
 * who said «Più tardi». It is an identifier, not a credential: the passkey is still the only way in.
 */
export function EmailAskDialog({ visible, onSave, onDismiss }: Props) {
  const { t } = useTranslation();
  const [email, setEmail] = useState('');
  const [busy, setBusy] = useState(false);
  const [error, setError] = useState<string | null>(null);

  const save = () => {
    if (!emailLooksValid(email)) {
      setError(t('sync.emailAskInvalid'));
      return;
    }
    setBusy(true);
    setError(null);
    void onSave(email.trim().toLowerCase())
      .then(() => {
        setEmail('');
        onDismiss();
      })
      .catch((caught: unknown) => {
        const code =
          typeof caught === 'object' && caught !== null && 'code' in caught
            ? String((caught as { code: unknown }).code)
            : '';
        setError(code === 'email_taken' ? t('sync.emailAskTaken') : t('sync.emailAskInvalid'));
      })
      .finally(() => setBusy(false));
  };

  return (
    <ConfirmDialog
      visible={visible}
      title={t('sync.emailAskTitle')}
      body={t('sync.emailAskBody')}
      confirmLabel={t('common.save')}
      cancelLabel={t('sync.emailAskLater')}
      onConfirm={save}
      onCancel={onDismiss}
      busy={busy}
    >
      <View style={{ gap: 8, marginTop: 12 }}>
        <TextField
          testID="email-ask-field"
          label={t('web.auth.emailLabel')}
          value={email}
          onChangeText={setEmail}
          autoCapitalize="none"
          autoCorrect={false}
          spellCheck={false}
          keyboardType="email-address"
          textContentType="emailAddress"
          returnKeyType="done"
          onSubmitEditing={save}
        />
        {error === null ? null : (
          <Text size="footnote" color="accent">
            {error}
          </Text>
        )}
      </View>
    </ConfirmDialog>
  );
}
```

## What changed while building (2026-09-28)

What the plan got wrong, and what was done instead. Each of these is committed with the task that hit it.

- **`afterVerification` runs with a session too, and the plan had no early return for it** (Task 7). With a session
  `@better-auth/passkey` skips `resolveUser` and still calls `afterVerification` — which is exactly what «add a
  passkey» from `/profile/passkeys` does. Without a guard, adding a second passkey would have re-checked the
  registration policy, burned an invite and tried to insert a user row that already exists. `completeRegistration`
  now returns early when the resolved id already names an account. Nothing exercised that path before 0.3b, so this
  was a latent bug, not a new one; it is written down in spec §17.1.4.
- **An empty passkey name is refused, not a reset** (Task 19). The plan said an empty field «puts the row back to
  «Passkey»». Better Auth validates `updatePasskey`'s `name` with `min(1)`, so that would have surfaced as an opaque
  failure. The action refuses an empty name and the dialog's «Salva» stays disabled while the field is empty; a row
  with no label already shows its authenticator's name. Commit `e676d79`.
- **`registrationGate.test.ts` had to be updated with the email** (Task 6). A pre-existing suite drives `resolveUser`
  through the real Better Auth API; once `email_required` landed it would have failed on the missing field instead of
  exercising invites. It now supplies an email, so it keeps testing what it was written to test.
- **Base UI's package is `@base-ui/react`** (Task 4, `^1.8.0`), and its parts are namespaced (`Dialog.Root`,
  `Dialog.Popup`, `AlertDialog.Description`) — the import path the plan assumed did not survive contact.
- **`session.ts`'s import order** was left unsorted when Task 8 was committed and biome caught it one task later; the
  fix rode along with `POST /api/me/email` (`1a5e824`) rather than as a commit of its own.
- **`EmailAskDialog`'s test waits needed five seconds, not the default one** (Task 21). Both assertions wait on a
  state change behind a promise; the whole workspace running in parallel exceeded the library's one-second budget
  once, failing a test that passes alone in three seconds. Five seconds still fails rather than hangs.
- **`ConfirmDialog` gained three optional props** (`children`, `busy`, `confirmTestID`/`cancelTestID`) so the phone's
  email ask could host a field inside it. Additive, so every existing caller is untouched — cheaper than a second
  dialog component.

Verification (Task 23): `pnpm lint` clean (`Checked 714 files`, no `lint/…` line, no `× Some errors`), `pnpm typecheck`
clean across five packages, `pnpm test` green — core 536, i18n 95, ui 81, mobile 743, web 266 (5 skipped: the S3
emulator suite, which is skipped unless one is running). `pnpm --filter web build` produces the standalone build, every

### Fixed

### Read and not changed

- **No component tests on the web** (`LoginForm`, `RegisterFlow`, `MobileAuth`, `PasskeyList`). Deliberate: §16 gives
  `apps/web` route handlers over PGlite and pure functions, and RNTL to the phone. Decided 2026-09-28 to keep it that
  way for 0.3b rather than add Testing Library mid-phase; the fixes above were verified by hand.
- **`/api/me/email` is check-then-update**, so two accounts claiming one address concurrently give the loser a 500
  instead of a 409. One person's instance, one address: left for 0.3f, which touches this route for verification.
- **The adapter's `transaction` option is off**, so the passkey plugin's transaction around registration is a
  pass-through. Turning it on would be worse, not better: `burnInvite`, `claimRoleForNewUser` and `attributeInvite`
  run on the outer handle and would sit outside it. Threading one transaction through both halves is a change to make
  on purpose, not as a review fix.
- **`normaliseEmail` accepts `…@passkey.saldo.invalid`**, so somebody could type the reserved domain into the email
  ask and stay «without an email» forever. Harmless to everybody else; worth a line in 0.3f with the rest of the
  address rules.
- **The invite check answers `{valid: true}` on a `closed` instance**, where no code is required; the ceremony then
  refuses with `registration_closed`. The step never shows on such an instance (`/register` redirects), so this is
  reachable only by calling the endpoint directly.
- **`userI18n` loads the whole projection for a locale.** Real waste, but it is the projection 0.3d needs on every
  page anyway; revisit when the read screens land.
- Minor polish left listed but not taken: `Button.module.css`'s literal `44px` (the token exists), the hard-coded mono
  stack, the phone's dialog using `web.auth.emailLabel`, `stepAfter` being unused, the unreferenced `.action` and
  `.dangerous` rules, `aria-errormessage` on `TextField`, the delete dialog not naming the passkey.
