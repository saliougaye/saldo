# 0.3f-2 — Server settings in the database, encrypted secrets, Impostazioni and SMTP

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or
> superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** an admin changes the registration mode, the instance name and the SMTP configuration from `/admin/settings`
without editing an env file or restarting; an environment variable that sets the same thing wins and locks it; the
SMTP password is encrypted at rest and write-only; «Manda un'email di prova» proves the configuration works.

**Architecture:** one table, `server_settings(key, value jsonb, updated_at, updated_by)`, read through one resolver
(`src/server/settings/`) that merges environment → database → default and says where each value came from. Everything
that read `env().registration` or `instanceInfo().name` asks the resolver instead. Secrets are AES-256-GCM under
`SETTINGS_ENCRYPTION_KEY`. Mail goes through one `sendMail` that builds its transport from the resolved configuration
at send time, so a change takes effect on the next message. The UI is 0.3f-1's Admin shell: summary rows, one panel
per setting (`/admin/settings?edit=name|registration|smtp`).

**Tech Stack:** as 0.3f-1, plus `nodemailer` (+ `@types/nodemailer`), current stable.

Depends on 0.3f-1 (the Admin shell, `requireWebAdmin`, `SlotPanel`). 0.3f-3 (verification, recovery) builds on
`sendMail` and the SMTP resolver of this plan.

## Decisions

1. **The table** (spec §17.1.8): `server_settings` — `key text primary key`, `value jsonb not null`,
   `updated_at timestamptz not null`, `updated_by text references user(id) on delete set null`. In
   `src/server/db/schema.ts`, added to `schema`, migration generated with `pnpm --filter web db:generate` (never
   hand-written), added to the harness's `truncate` list and to whatever `schema.test.ts` enumerates. Three keys:
   `registration` (a mode string), `instanceName` (a string), `smtp` (an object, decision 5). A missing row means
   «not set here».
2. **Precedence, in one pure function.** `resolveSettings(envPart, rows)` in `src/server/settings/resolve.ts`
   (+ test, no database): for each setting `{ value, source: 'env' | 'database' | 'default', envVar: string | null }`.
   - **Registration:** `REGISTRATION` set → env, locked. Else the row. Else `'first-user'`, today's default. So
     `REGISTRATION` becomes **optional** in `env.ts` (`ServerEnv.registration: RegistrationMode | null`); an instance
     that sets it keeps working exactly as before, and one that removes it chooses in the panel.
   - **Instance name:** new optional `INSTANCE_NAME` (1–60 characters after trim) → env, locked. Else the row. Else
     `WEBAUTHN_RP_NAME`, which is what the sign-in page has always shown. `WEBAUTHN_RP_NAME` stays required and stays
     the passkey relying-party name (infrastructure, §17.1.8).
   - **SMTP:** new optional `SMTP_HOST`, `SMTP_PORT` (default 587), `SMTP_USER`, `SMTP_PASSWORD`, `SMTP_FROM`. When
     `SMTP_HOST` is set the **whole group** comes from the environment and is locked (`SMTP_FROM` is then required;
     `SMTP_USER` and `SMTP_PASSWORD` come together or not at all — `env.ts` reports each by name, as the storage
     driver's variables are). Else the row. Else not configured (`value: null`).
   A stored row that no longer parses (a hand-edited value) reads as not set, and is logged — it never breaks a page.
3. **`SETTINGS_ENCRYPTION_KEY` is required** (spec §17.1.8): 32 random bytes, base64 (`openssl rand -base64 32`);
   `env.ts` refuses anything that does not decode to exactly 32 bytes, naming the variable. Added to `vitest.config.mts`
   (an obviously fake key), `.env.example` with the command, both docker-compose files, `docs/self-hosting.md` (with an
   **upgrade note**: an existing instance must add it before starting this version, and must keep it — losing it
   loses the stored SMTP password, nothing else), and spec §9.2. If `apps/web/.env` exists locally and lacks it,
   append a freshly generated one (that file is untracked and is what `pnpm --filter web dev` reads); never print or
   commit a real key.
4. **Encryption** in `src/server/settings/secret.ts` (+ test): `encryptSecret(plain, key, slot)` and
   `decryptSecret(stored, key, slot)` with `node:crypto` AES-256-GCM, a random 12-byte IV per call, the 16-byte tag,
   and the **slot name as additional authenticated data** (`'smtp.password'`), so a ciphertext copied into another
   setting does not decrypt. Stored as the string `v1:{iv}:{tag}:{ciphertext}`, each part base64. `decryptSecret`
   returns `null` — never throws — for a wrong key, a wrong slot, a tampered or malformed value. Tests: round trip;
   two encryptions of one value differ; each of the four failures gives `null`; the stored form has no plaintext.
5. **The `smtp` row**: `{ host, port, user: string | null, password: string | null /* the v1 envelope */, from }`.
   `secure` is not stored: port 465 is implicit TLS; any other port **requires STARTTLS** (`requireTLS: true`), except
   when the host is `localhost`, `127.0.0.1` or `::1` (a development catcher such as Mailpit), where a plain
   connection is allowed. The rule is one pure function (`transportSecurity(host, port)`, tested).
   What pages and actions get is `SmtpView`: `{ host, port, user, from, passwordSet: boolean, passwordReadable: boolean }`
   — **no function that serves the UI returns the password or its envelope**. Only `smtpForSending(db)` decrypts.
   A password that no longer decrypts (the key changed) makes `passwordReadable` false: the panel says «la password
   non si legge più con la chiave attuale: reinseriscila», and sending answers `notConfigured`.
6. **Reading.** `src/server/settings/serverSettings.ts`: `readServerSettings(db)` → the three resolved settings (one
   query: all rows), plus the narrow helpers the callers want — `registrationMode(db)`, `instanceName(db)`. Replace
   every reader (grep `env().registration`, `instanceInfo(`, `rpName`):
   - `auth.ts`: the mode is no longer captured when the instance is built — `resolveUser` and `afterVerification`
     call `registrationMode(db)` at ceremony time, and `invitePlugin` takes a getter. A test pins that a mode saved in
     the table is honoured by the **next** `resolveRegistration` without rebuilding `auth()`.
   - `/api/health`, `/login`, `/register`, `/auth/mobile`, `/onboarding`, the Admin head, the invite panel:
     `instanceInfo()` becomes `async instanceInfo(db)` with the resolved name; modes come from `registrationMode`.
   Pages wrap the read in React's `cache()` (one query per request); route handlers and auth hooks just query — it is
   one indexed read of a three-row table.
7. **Writing**, in `src/server/settings/write.ts` (+ test), results not throws:
   `{ ok: true } | { ok: false; error: 'locked' | 'invalid' }`. **`locked` is decided on the server** from the
   resolver, not from what the form showed.
   - `saveRegistration(db, actorId, raw, now)` — one of the four modes.
   - `saveInstanceName(db, actorId, raw, now)` — trimmed, 1–60; `clearInstanceName` is saving the empty string: the
     row is deleted and the name falls back to `WEBAUTHN_RP_NAME` (the panel's hint says so).
   - `saveSmtp(db, actorId, raw, now)` — host (1–255, no spaces), port (1–65535), user (optional, ≤255), from (a
     mailbox: `name <addr>` or `addr`; validate the address part with the zod email rule `email.ts` already uses),
     and `password`: **absent = keep the stored one, a string = replace it (encrypted), `null` = remove it**. User
     without a password and password without a user are `invalid`. **Keeping** the stored password is allowed only
    while `host` and `user` equal the stored row's; otherwise the result is `passwordRequired` (so a session cannot
    redirect the stored password to another server). Port and sender may change while keeping it.
   - `removeSmtp(db, actorId)` — deletes the row: mail is off again.
   Every write stamps `updated_at`/`updated_by` and upserts on `key`.
8. **Mail** in `src/server/mail/mailer.ts` (+ test): `sendMail(db, { to, subject, text }, source?)` →
   `{ ok: true } | { ok: false; error: 'notConfigured' | 'failed'; detail?: string }`. It resolves the configuration,
   builds a nodemailer transport **for this message** (connection and greeting timeouts of 10 s, so an unreachable
   host fails an action instead of hanging it), sends, closes. Plain text only — no HTML templates in 0.3f.
   `detail` is the transport's error message, shown **only to an admin** (the test-email panel); log it without the
   recipient's address. The transport factory is injectable (`setMailTransportForTests`), and tests use nodemailer's
   own `jsonTransport` or a fake — no test opens a socket. `mailEnabled(db)` answers whether `sendMail` could work.
   Read nodemailer's types for the exact option names and follow them.
9. **«Manda un'email di prova»** sends to the **signed-in admin's own address** — no free recipient field, so the
   panel cannot be used to mail strangers. It uses the **saved** configuration: while the form has unsaved changes
   the button is disabled and says «Salva prima». An admin whose address is synthetic is told to set a real email
   first. Success names the address it went to; failure shows `detail`.
10. **`/admin/settings`** (mockup: `panelsContent` default branch, `namePanel`, `lockedPanel`, `smtpPanel`). Section
    «Impostazioni del server», trailing «cambiano senza riavviare». Three summary rows:
    - «Nome dell'istanza» — subtitle «nella pagina d'accesso e negli inviti», value the name; `?edit=name`.
    - «Registrazione» — value the mode's label; `?edit=registration`.
    - «Email (SMTP)» — subtitle `host:port · user` or «non configurata», value «configurata» with the ok dot or
      nothing; `?edit=smtp`.
    A row whose setting is locked shows «impostato dall'ambiente» as its subtitle. Anything else in `?edit=` opens
    nothing. «Impostazioni» joins Admin's sub-navigation after Istanza.
    - **A locked panel** (any of the three): an alert «Impostata dall'ambiente» naming the variable(s) — the value is
      shown for `REGISTRATION` and `INSTANCE_NAME`, **never for `SMTP_PASSWORD`** — and how to change it (edit it
      where the server runs and restart, or remove it and choose here); the choices shown disabled; no save button.
      For SMTP the test email stays available, since the environment's configuration can be tested too.
    - **Registration**: the four modes as a radio list (label + one line each: Aperta / Solo il primo / Solo con
      invito / Chiusa, as the mockup). Unlike Profilo's preferences it is **not** saved on choice: opening
      registration by a mis-click is not a mistake to make easy. «Salva» writes; ⌘↵ saves. If `OptionList`
      (`app/(app)/profile/preferences/`) fits, move it to `src/ui/` and reuse it rather than writing a second.
    - **Name**: one field, the hint «Lo vede chi apre la pagina d'accesso o riceve un invito. Vuoto: torna il nome
      predefinito.», «Salva».
    - **SMTP**: Server + Porta on one line, Utente, Password, Mittente. With a stored password the field is replaced
      by «impostata» and «Sostituisci» (which reveals an empty `type="password"` field with
      `autocomplete="new-password"`; the stored value is never sent to the browser); hint «Cifrata sul server. Non si
      rilegge: si sostituisce.» Foot: «Manda un'email di prova» leading, «Salva» trailing, and when a row exists
      «Rimuovi configurazione» (asks). The note «Serve per verificare le email e recuperare l'accesso. Senza, la
      registrazione funziona lo stesso.» sits under the title.
11. **Strings**: `admin.settings.*` in the seven catalogs; the test email's subject and body are `admin.mail.*` and
    are sent in the **admin's** language. Same rules as 0.3f-1 decision 13.
12. **Not here:** verification and recovery (0.3f-3); the AI key (0.5) — but `secret.ts`'s slot argument is what it
    will reuse; HTML mail; key rotation (documented: change the key → re-enter the SMTP password).
