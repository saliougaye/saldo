# Phase 10 — Access control: who is allowed in

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or
> superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** the person who installs the server decides who gets an account, and can throw someone out afterwards.

**Architecture:** `REGISTRATION` gains a fourth value, `invite`, under which **no account is ever created without a
single-use code** — not even the first. The first code is minted with a CLI on the server, so the first account to
exist belongs, by construction, to whoever has shell access to the box; that account is given the `admin` role and
every later one gets `user`. Roles, revocation and the user list come from Better Auth's `admin` plugin rather than
from hand-written code, the same decision phase 06b made for the ceremonies themselves. Invites are ours: a table of
**hashed** codes, validated when the WebAuthn ceremony starts and burned by a conditional `UPDATE` when it succeeds,
so two people racing on one code cannot both get in and an abandoned ceremony spends nothing.

This phase ships the server and the CLI only. The app grows no screen: the invite code is typed into `/auth/mobile`,
which the **server** serves, so `apps/mobile` is untouched.

**Tech Stack:** Next.js 16 App Router route handlers, Better Auth 1.7.4 (`admin` plugin), Drizzle + Postgres,
`node:crypto`, Zod 4, Vitest against PGlite, `tsx` for the CLI.

**Branch:** `phase/10-access-control` (already created).

## Facts checked in the installed libraries (do not re-litigate)

- `@better-auth/passkey@1.7.4`: `registration.resolveUser({ ctx, context })` and
  `registration.afterVerification({ ctx, verification, user, clientData, context })`. `context` is **one optional
  string**, stored on the challenge (`WebAuthnChallengeValue.context`), so the same value reaches both callbacks.
  That is the only channel from the browser form into the server hooks, which is why the invite code travels inside
  it as JSON.
- `better-auth@1.7.4`'s `admin` plugin adds to `user`: `role` (string), `banned` (boolean, default false),
  `banReason` (string), `banExpires` (date); and to `session`: `impersonatedBy` (string). Defaults:
  `defaultRole: 'user'`, `adminRoles: ['admin']`.
- The plugin's ban enforcement is a `session.create.before` hook — it blocks **new** sessions. An **existing** bearer
  dies because `banUser` deletes the user's session rows, not because `getSession` re-checks the flag. This plan
  therefore does both: revocation deletes the sessions **and** `requireUser` refuses a banned user, so the invariant
  holds even if a session row is ever left behind.

## Task 1: The invite code

A code is typed by a human, out of a message, into a phone browser. It is 16 symbols of Crockford's base32 (80 bits
of entropy — brute force is not a threat model), grouped in fours, and normalisation maps the four characters that
get misread (`I`, `L` → `1`, `O` → `0`, `U` → `V`) so a code read off a screen works whatever the reader assumed.

```ts
    expect(normaliseInviteCode('7gq4xm2bpdvt9nks')).toBe(canonical);
    expect(normaliseInviteCode('  7GQ4 XM2B PDVT 9NKS  ')).toBe(canonical);
  });

  it('folds the symbols that get misread', () => {
    // O→0, I→1, L→1, U→V: a code read off a screen works whatever the reader assumed.
    expect(normaliseInviteCode('O1IL-UUUU-0000-1111')).toBe('01110VVVV00001111');
  });

  it('drops anything that is not a symbol, so punctuation cannot change the answer', () => {
    expect(normaliseInviteCode('7GQ4/XM2B.PDVT_9NKS')).toBe(normaliseInviteCode('7GQ4XM2BPDVT9NKS'));
  });
});

describe('hashInviteCode', () => {
  it('is stable across every spelling of the same code', () => {
    const code = generateInviteCode();
    expect(hashInviteCode(code.toLowerCase())).toBe(hashInviteCode(code));
    expect(hashInviteCode(code.replace(/-/g, ''))).toBe(hashInviteCode(code));
  });

  it('is a sha-256 hex digest, so the table never holds a usable code', () => {
    const hash = hashInviteCode('7GQ4-XM2B-PDVT-9NKS');
    expect(hash).toMatch(/^[0-9a-f]{64}$/);
    expect(hash).not.toContain('7GQ4');
  });

  it('separates two codes that differ by one symbol', () => {
    expect(hashInviteCode('7GQ4-XM2B-PDVT-9NKS')).not.toBe(hashInviteCode('7GQ4-XM2B-PDVT-9NKT'));
  });
});
```

Note the third `normaliseInviteCode` expectation: `'O1IL-UUUU-0000-1111'` folds to `01110VVVV00001111`, which is 17
symbols, because `normalise` does not care about length — it only canonicalises. Length is the database's problem:
an unknown hash is refused like any other.

Create `apps/web/src/server/auth/inviteCode.ts`:

```ts
import { createHash, randomBytes } from 'node:crypto';

/**
 * Crockford's base32: no `I`, `L`, `O` or `U`, so no two symbols look alike in a message and none
 * of them can spell a word by accident. 32 symbols is exactly 5 bits, which is what lets the
 * generator slice random bytes without biasing the result.
 */
const ALPHABET = '0123456789ABCDEFGHJKMNPQRSTVWXYZ';
const GROUPS = 4;
const GROUP_SIZE = 4;
const LENGTH = GROUPS * GROUP_SIZE;

/** What a person may type instead of the symbol that is actually in the alphabet. */
const FOLD: Record<string, string> = { I: '1', L: '1', O: '0', U: 'V' };

/** 16 symbols of a 32-symbol alphabet: 80 bits, formatted `XXXX-XXXX-XXXX-XXXX`. */
export function generateInviteCode(): string {
  const bytes = randomBytes(LENGTH);
  let symbols = '';
  for (const byte of bytes) {
    // The low 5 bits of a uniform byte are themselves uniform over 0-31, so no rejection sampling.
    symbols += ALPHABET[byte & 31] ?? '0';
  }
  const groups: string[] = [];
  for (let i = 0; i < LENGTH; i += GROUP_SIZE) groups.push(symbols.slice(i, i + GROUP_SIZE));
  return groups.join('-');
}

/**
 * The canonical spelling of whatever was typed: upper case, ambiguous characters folded, and
 * everything that is not a symbol removed — so dashes, spaces and a stray full stop from a chat
 * client all lead to the same answer.
 */
export function normaliseInviteCode(raw: string): string {
  let out = '';
  for (const character of raw.toUpperCase()) {
    const folded = FOLD[character] ?? character;
    if (ALPHABET.includes(folded)) out += folded;
  }
  return out;
}

/**
 * The table stores this, never the code: a leaked database backup does not let anybody register.
 * A plain digest and not a password hash on purpose — this is 80 random bits, not a secret a
 * person chose, so there is nothing for a slow hash to defend.
 */
export function hashInviteCode(raw: string): string {
  return createHash('sha256').update(normaliseInviteCode(raw), 'utf8').digest('hex');
}
```

```ts
/**
 * §9.2 `REGISTRATION`: `open` always, `closed` never, `first-user` only while the instance has no
 * user — which is how a fresh self-hosted server lets its owner in and then shuts the door — and
 * `invite` always, because under that mode it is the **code** that decides, not the instance.
 *
 * What this answers is "should the client offer to create an account", which is why `invite` is
 * `true`: somebody holding a code must be able to reach the form. Whether the code is any good is
 * settled later, in `resolveUser`.
 *
 * Better Auth has no notion of a closed instance, so this is checked in the passkey plugin's
 * `resolveUser` hook: the last moment before a user row would be created.
 */
export async function registrationAllowed(
  db: ServerDatabase,
  mode: RegistrationMode,
): Promise<boolean> {
  if (mode === 'open' || mode === 'invite') return true;
  if (mode === 'closed') return false;
  const [row] = await db.select({ count: sql<number>`count(*)::int` }).from(user);
  return (row?.count ?? 0) === 0;
}

/**
 * Under `invite` **every** account needs a code, including the first: the first code is minted by
 * the CLI on the server, so the first account to exist is the one belonging to whoever installed
 * it. That is the whole of §10's "who is allowed in" — there is no window during which the door
 * stands open.
 */
export function registrationRequiresInvite(mode: RegistrationMode): boolean {
  return mode === 'invite';
}
```

## Task 4: The invite service

The heart of the phase. Two rules carry the security of the whole thing:

1. **An invite is burned by a conditional `UPDATE`, never by read-then-write.** Postgres takes a row lock on the
   matching row, so of two ceremonies racing on one code exactly one `UPDATE` returns a row and the other returns
   none. A `SELECT` followed by an `UPDATE` would let both through.
2. **Expiry is `>` and not `>=`.** Phase 06's review found every expiry in the codebase usable *at* its deadline;
   this one is written the right way round from the start and has a boundary test.

```ts
import { and, desc, eq, gt, isNull } from 'drizzle-orm';
import { invites } from '../db/schema';
import type { ServerDatabase } from '../db/types';
import { generateInviteCode, hashInviteCode } from './inviteCode';

export const DEFAULT_INVITE_TTL_DAYS = 7;
export const MAX_INVITE_TTL_DAYS = 90;
export const MAX_INVITE_LABEL_LENGTH = 80;

const DAY_MS = 24 * 60 * 60 * 1000;

/** What an invite is, once it is no longer a code. `used` wins over `revoked`: it already worked. */
export type InviteStatus = 'active' | 'used' | 'revoked' | 'expired';

export interface InviteSummary {
  id: string;
  label: string | null;
  createdAt: string;
  expiresAt: string;
  usedAt: string | null;
  usedBy: string | null;
  revokedAt: string | null;
  status: InviteStatus;
}

interface InviteRow {
  id: string;
  label: string | null;
  createdAt: Date;
  expiresAt: Date;
  usedAt: Date | null;
  usedBy: string | null;
  revokedAt: Date | null;
}

export interface CreateInviteInput {
  label: string | null;
  ttlDays: number;
  /** Null when the CLI minted it: it runs with no session, and on a fresh server there is none. */
  createdBy: string | null;
  now: Date;
}

function summarise(row: InviteRow, now: Date): InviteSummary {
  return {
    id: row.id,
    label: row.label,
    createdAt: row.createdAt.toISOString(),
    expiresAt: row.expiresAt.toISOString(),
    usedAt: row.usedAt?.toISOString() ?? null,
    usedBy: row.usedBy,
    revokedAt: row.revokedAt?.toISOString() ?? null,
    status:
      row.usedAt !== null
        ? 'used'
        : row.revokedAt !== null
          ? 'revoked'
          : row.expiresAt.getTime() <= now.getTime()
            ? 'expired'
            : 'active',
  };
}

/**
 * The one moment the code exists in the clear. It is returned to the caller and nowhere else: the
 * row holds a sha-256, so this value cannot be recovered from the server afterwards.
 */
export async function createInvite(
  db: ServerDatabase,
  input: CreateInviteInput,
): Promise<{ code: string; invite: InviteSummary }> {
  const code = generateInviteCode();
  const row = {
    id: crypto.randomUUID(),
    codeHash: hashInviteCode(code),
    label: input.label,
    createdBy: input.createdBy,
    createdAt: input.now,
    expiresAt: new Date(input.now.getTime() + input.ttlDays * DAY_MS),
    usedAt: null,
    usedBy: null,
    revokedAt: null,
  };
  await db.insert(invites).values(row);
  return { code, invite: summarise(row, input.now) };
}

/** The conditions under which a code opens the door, in one place so the two callers agree. */
function usableWhere(codeHash: string, now: Date) {
  return and(
    eq(invites.codeHash, codeHash),
    isNull(invites.usedAt),
    isNull(invites.revokedAt),
    // `>` and not `>=`: an invite is dead **on** its deadline, not a second after it.
    gt(invites.expiresAt, now),
  );
}

/**
 * Asked before the WebAuthn ceremony starts, so a bad code fails before the phone asks for a
 * fingerprint. It deliberately does not say *why* a code is no good — unknown, spent, revoked and
 * expired are one answer to the caller, so the form cannot be used to probe the table.
 */
export async function inviteIsUsable(db: ServerDatabase, code: string, now: Date): Promise<boolean> {
  const [row] = await db
    .select({ id: invites.id })
    .from(invites)
    .where(usableWhere(hashInviteCode(code), now));
  return row !== undefined;
}

/**
 * Spends the invite, returning its id, or null if there was nothing to spend. One conditional
 * `UPDATE`: Postgres locks the matching row, so of two ceremonies racing on one code exactly one
 * gets a row back. Reading first and writing after would let both of them in.
 */
export async function burnInvite(
  db: ServerDatabase,
  code: string,
  userId: string,
  now: Date,
): Promise<string | null> {
  const [row] = await db
    .update(invites)
    .set({ usedAt: now, usedBy: userId })
    .where(usableWhere(hashInviteCode(code), now))
    .returning({ id: invites.id });
  return row?.id ?? null;
}

/**
 * Undoes a burn. The registration hook spends the invite **before** it writes the account, so that
 * two ceremonies cannot both proceed; if the write then fails, the person still holds a code that
 * never let them in, and this is what makes it work again.
 */
export async function releaseInvite(db: ServerDatabase, id: string): Promise<void> {
  await db.update(invites).set({ usedAt: null, usedBy: null }).where(eq(invites.id, id));
}

export async function listInvites(db: ServerDatabase, now: Date): Promise<InviteSummary[]> {
  const rows = await db
    .select({
      id: invites.id,
      label: invites.label,
      createdAt: invites.createdAt,
      expiresAt: invites.expiresAt,
      usedAt: invites.usedAt,
      usedBy: invites.usedBy,
      revokedAt: invites.revokedAt,
    })
    .from(invites)
    .orderBy(desc(invites.createdAt));
  return rows.map((row) => summarise(row, now));
}

/** Reports whether there was an invite to revoke, so the route can answer 404 rather than lie. */
export async function revokeInvite(db: ServerDatabase, id: string, now: Date): Promise<boolean> {
  const [row] = await db
    .update(invites)
    .set({ revokedAt: now })
    .where(and(eq(invites.id, id), isNull(invites.revokedAt)))
    .returning({ id: invites.id });
  return row !== undefined;
}
```

```ts
import { asc, eq, sql } from 'drizzle-orm';
import { session, user } from '../db/schema';
import type { ServerDatabase } from '../db/types';

/**
 * The role better-auth's `admin` plugin treats as an administrator (its `adminRoles` default), and
 * the one `requireAdmin` checks. Saldo has exactly two roles: this, and everybody else.
 */
export const ADMIN_ROLE = 'admin';
export const MEMBER_ROLE = 'user';

export interface AccountSummary {
  id: string;
  displayName: string;
  role: string;
  revoked: boolean;
  revokedReason: string | null;
  createdAt: string;
}

/**
 * §9.5. The first account on the instance is the admin. Under `REGISTRATION=invite` that account
 * can only be created with a code minted by the CLI, so "the first account" and "whoever installed
 * this server" are the same person by construction — there is no race to win.
 */
export async function roleForNewUser(db: ServerDatabase): Promise<string> {
  const [row] = await db.select({ count: sql<number>`count(*)::int` }).from(user);
  return (row?.count ?? 0) === 0 ? ADMIN_ROLE : MEMBER_ROLE;
}

/** A revoked account is not an admin, whatever its role says. */
export async function isAdmin(db: ServerDatabase, userId: string): Promise<boolean> {
  const [row] = await db
    .select({ role: user.role, banned: user.banned })
    .from(user)
    .where(eq(user.id, userId));
  if (row === undefined || row.banned === true) return false;
  return row.role === ADMIN_ROLE;
}

export async function isRevoked(db: ServerDatabase, userId: string): Promise<boolean> {
  const [row] = await db.select({ banned: user.banned }).from(user).where(eq(user.id, userId));
  return row?.banned === true;
}

/**
 * Throws somebody out without destroying anything they wrote. Two writes, both needed: the flag
 * stops better-auth from ever creating another session for them, and deleting the session rows
 * kills the bearer they are holding right now — the plugin's own check runs at session *creation*,
 * so it would not touch a live one.
 */
export async function revokeUser(
  db: ServerDatabase,
  userId: string,
  reason: string | null,
  now: Date,
): Promise<boolean> {
  const [row] = await db
    .update(user)
    .set({ banned: true, banReason: reason, banExpires: null, updatedAt: now })
    .where(eq(user.id, userId))
    .returning({ id: user.id });
  if (row === undefined) return false;
  await db.delete(session).where(eq(session.userId, userId));
  return true;
}

export async function restoreUser(db: ServerDatabase, userId: string): Promise<boolean> {
  const [row] = await db
    .update(user)
    .set({ banned: false, banReason: null, banExpires: null })
    .where(eq(user.id, userId))
    .returning({ id: user.id });
  return row !== undefined;
}

/** Irreversible: the foreign keys carry away the sessions, the passkeys and every synced row. */
export async function deleteUser(db: ServerDatabase, userId: string): Promise<boolean> {
  const [row] = await db.delete(user).where(eq(user.id, userId)).returning({ id: user.id });
  return row !== undefined;
```

```ts
import { z } from 'zod';

/**
 * `@better-auth/passkey` passes exactly one optional string from the client into `resolveUser` and
 * stores it on the challenge, so the same value reaches `afterVerification`. That single channel
 * has to carry both things the registration form collects, which is why it is JSON.
 */
export interface RegistrationContext {
  name: string;
  invite: string | null;
}

const schema = z.object({
  name: z.string(),
  invite: z.string().optional(),
});

/**
 * The canonical encoder. `MobileAuth.tsx` is a client component and deliberately does not import
 * it — nothing from `src/server` belongs in a bundle sent to a browser — so it writes the same
 * JSON by hand, and `registrationContext.test.ts` pins the literal shape both must produce.
 */
export function encodeRegistrationContext(value: {
  name: string;
  invite?: string | undefined;
}): string {
  return JSON.stringify({ name: value.name, invite: value.invite });
}

/**
 * Never throws: this reads client-supplied data, and every way of getting it wrong has to end in
 * the same place — an empty name and no code, which the caller refuses like any other bad input.
 * A value that is not JSON is read as a bare display name, which is what the form sent before
 * invites existed.
 */
export function readRegistrationContext(context: string | null | undefined): RegistrationContext {
  if (context === null || context === undefined) return { name: '', invite: null };
  let raw: unknown;
  try {
    raw = JSON.parse(context);
  } catch {
    return { name: context.trim(), invite: null };
  }
  const parsed = schema.safeParse(raw);
  if (!parsed.success) return { name: '', invite: null };
  return { name: parsed.data.name.trim(), invite: parsed.data.invite?.trim() ?? null };
}
```

```ts
import { auth } from '../auth/auth';
import { isRevoked } from '../auth/admin';

export interface AuthenticatedUser {
  id: string;
  displayName: string;
}

/**
 * Every bearer route starts here, and every query downstream scopes on the id it returns. The
 * `bearer` plugin lets `getSession` read the token out of the Authorization header, so this is the
 * same call a cookie-bearing browser would make — session expiry and revocation are Better Auth's.
 *
 * The revocation check is ours and is deliberately not left to the library: better-auth only tests
 * the ban flag when a session is **created**, so a live bearer would survive until its session row
 * happened to be deleted. §10 promises that a revoked account stops syncing at once, and that
 * promise is kept here rather than by remembering to delete rows everywhere else.
 */
export async function requireUser(request: Request): Promise<AuthenticatedUser> {
  const session = await auth().api.getSession({ headers: request.headers });
  if (session === null) throw new ApiError(401, 'unauthorized', 'A bearer token is required');
  if (await isRevoked(getDb(), session.user.id)) {
    throw new ApiError(401, 'unauthorized', 'This account no longer has access');
  }
  return { id: session.user.id, displayName: session.user.name };
}
```

```markdown
### 9.5 Access control: invites and revocation

`REGISTRATION=invite` is the mode a shared instance runs in. Under it **no account is created
without a single-use code** — not even the first one, which is what makes "the first account" and
"the person who installed the server" the same person rather than a race.

**The invite.** 16 symbols of Crockford's base32 (`I`, `L`, `O` and `U` are absent; a reader's
substitutions are folded on the way in), formatted `XXXX-XXXX-XXXX-XXXX` — 80 bits. The `invites`
table stores its **sha-256**, a label, who minted it, a TTL (7 days by default, 90 at most) and
what became of it. A code is shown exactly once, by the thing that mints it.

The ceremony touches it twice. `resolveUser` **checks** the code before WebAuthn starts, so a bad
code costs nobody a fingerprint and an abandoned ceremony costs nobody their invite;
`afterVerification` **burns** it with a single conditional `UPDATE`, so two people racing on one
code produce exactly one account. If writing the account then fails, the burn is released.
Unknown, spent, revoked and expired all answer `invalid_invite`: the form cannot be used to learn
which codes exist.

**Roles.** Better Auth's `admin` plugin (`user.role`, `user.banned`, `user.banReason`,
`user.banExpires`, `session.impersonated_by`). The first account on the instance gets `admin`,
every later one `user`. `requireAdmin` answers 401 without a session and 403 with the wrong
account.

**Revocation** keeps the account and everything it wrote: the ban flag stops any new session and
deleting the session rows kills the bearer in hand. The plugin's own check runs only when a
session is created, so `requireUser` tests the flag on every authenticated request — which is what
makes "a revoked account stops syncing" true immediately rather than eventually. Deleting an
account instead is irreversible and takes its `sync_rows` with it, by foreign key.

**Routes** (all admin-only): `POST /api/invites` mints, `GET /api/invites` lists (never a code),
`DELETE /api/invites/{id}` revokes. `/api/health` reports `inviteRequired`.

**CLI**, run on the server against `DATABASE_URL`, and the only thing that works when no account
exists: `pnpm --filter web invite new|list|revoke` and
`pnpm --filter web user list|revoke|restore|promote|delete`. `user promote` is the way back in if
the owner loses their phone.
```
