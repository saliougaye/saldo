# 0.3f-1 — Admin: the shell, Account, Inviti, Istanza

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or
> superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** an admin opens `/admin` and manages the instance's accounts (inspect, promote, revoke, restore, delete) and
invites (mint with the code shown once as text, link and QR; inspect; revoke), and reads what the instance is
(version, API, sync schema, storage, address, default time zone). No CLI needed for any of it.

**Architecture:** the Profilo pattern with no exception (§17.1.7, Admin, variant «3»): a layout with a sub-navigation,
each section a list of summary rows, each row inspected or edited in the trailing panel, the URL carrying the selection
(`/admin/accounts?u={id}`, `/admin/invites?new`, `?i={id}`). Pages are server components that read through
`src/server/auth/admin.ts` and `invites.ts` (the functions the CLI already calls), pure view functions in
`src/features/admin/` turn rows into what is rendered, and Server Actions in `app/(app)/admin/**/actions.ts` each start
with `requireWebAdmin()` and hand the rest to `src/server/admin/`.

**Tech Stack:** as 0.3e (Next 16 App Router, CSS Modules on token variables, Base UI, Drizzle, PGlite tests), plus one
new dependency: a QR encoder (`qrcode`, current stable, with `@types/qrcode`).

0.3f is three plans on `phase/0.3f-admin`, in order: **0.3f-1** (this one), **0.3f-2** (`server_settings`, encryption,
Impostazioni, SMTP), **0.3f-3** (email verification and recovery). «Impostazioni» is therefore **not** in the
sub-navigation yet: no link to a page that does not exist.

## Decisions

1. **Who gets in.** `requireWebAdmin()` in `src/server/auth/currentUser.ts`: `requireWebUser()`, then `isAdmin`; a
   signed-in member gets `notFound()` (a 404 says nothing about what is there), nobody signed in goes to `/login` as on
   every page. The layout calls it, **and so does every page and every Server Action** — a layout does not run for an
   action, and a page can be rendered without its layout re-running.
2. **URLs.** `/admin` redirects to `/admin/accounts`. `/admin/accounts` (`?u={id}` opens the account's panel),
   `/admin/invites` (`?new` opens «Nuovo invito», `?i={id}` an invite's panel; `?new` wins), `/admin/instance`. An id
   that names nothing opens no panel. Every row is an `<a href>`.
3. **The shell is shared with Profilo, not copied.** The layout classes both need (`layout`, `subnav`, `section`,
   `slot`, `separator`) and the portal move to `src/ui/`: `SlotPanel.tsx` (the component `ProfilePanel` is today,
   exporting `SlotPanel` and `PANEL_SLOT`), and `app/(app)/profile/ProfilePanel.tsx` + `panelSlot.ts` become one-line
   re-exports so no Profilo page changes. Admin's layout uses the same CSS module classes Profilo's does — read
   `app/(app)/profile/layout.tsx` and `profile.module.css`, move the shared classes into
   `src/ui/SubnavLayout.module.css` (+ a small `SubnavLayout.tsx` taking `nav`, `children`, and rendering the slot),
   and make Profilo's layout use it. Profilo must look and behave exactly as before.
4. **Admin head.** «Admin» as `h1`, and under it `{instance name} · {N} account` (`admin.headCount`, plural). The
   sub-navigation: Account (count of accounts), Inviti (count of **active** invites), Istanza. Icons: `settings`→ use
   the ones `@saldo/ui` has (`key` for Inviti, `info` for Istanza; read `packages/ui/src/icons.ts` for Account — a
   person/user icon if one exists, else `shield`).
5. **Account list.** One `SummaryRow`/`ListRow` per account, oldest first (`listAccounts`'s order): an initials avatar,
   the display name, the email under it (a synthetic address, `isSyntheticEmail`, shows `admin.noEmail` instead of
   `…@passkey.saldo.invalid`), the role on the trailing side, and «· revocato» for a revoked one, whose row is muted.
   The section's trailing text: «N account · M revocati» (M omitted at 0).
6. **Account panel** (`?u=`). New server function `accountDetail(db, userId)` in `admin.ts` returning the summary plus:
   `emailVerified`, `lastSignInAt` (the newest `session.created_at` of the account, null when it has none — a session
   row is written at sign-in, so this is the last **sign-in**, not the last request; the mockup's «dal telefono» is
   dropped: nothing reliable says which device), `passkeyCount`, `syncedRows` (`count(*)` of `sync_rows`), and
   `invite: { id, label } | null` (the invite whose `used_by` is this account). Shown as a fact list: Ruolo, Stato
   (attivo / revocato + reason), Email (verificata / non verificata), Creato (date, «con l'invito «X»» when there is
   one), Ultimo accesso, Passkey, Righe sincronizzate. Dates through `@saldo/i18n` formatters in the admin's locale
   and zone (`todayFor`/`settings.timeZone` as pages do — read `src/server/page/context.ts`; an admin who has not
   onboarded has no settings: fall back to `env().defaultTimeZone`, and **do not** redirect `/admin` to `/onboarding`).
7. **Account actions**, in `src/server/admin/accounts.ts` (+ test), each returning a result, never throwing for a
   refusal: `{ ok: true } | { ok: false; error: 'self' | 'notFound' | 'emailMismatch' }`.
   - `promoteAccount(db, actorId, targetId)` — «Rendi admin». No demote (the spec offers none; the CLI has none), so
     **it asks first** in a `ConfirmDialog` («Rendere {{name}} amministratore?»: an admin manages accounts, invites and
     the server's settings; it cannot be undone from here). Offered only for a member who is not revoked.
   - `revokeAccount(db, actorId, targetId, now)` / `restoreAccount(db, actorId, targetId)` — «Revoca accesso» asks in
     a `ConfirmDialog` (sessions close at once, data stays, can be restored); «Ripristina accesso» does not ask.
   - `deleteAccount(db, store, actorId, { id, confirmation })` — in a «Zona pericolosa» block; the dialog names the account,
     says how many synced rows go with it, and has a field where **the account's email must be typed**; the confirm
     button is disabled until it matches (trimmed, case-insensitive), and the server checks it again
     (`emailMismatch`). An account with a synthetic address is confirmed by typing its **display name** instead (the
     address is not shown, so it cannot be asked for) — the dialog's label says which.
   - **`self` is refused for revoke and delete**: an admin cannot lock themselves out from the panel. Since only an
     admin reaches these actions, this is also what guarantees the instance never loses its last admin. The panel of
     one's own account shows the facts and says why there are no actions (`admin.accounts.selfNote`).
   - **Deleting takes the attachment bytes too.** `deleteUser` cascades the rows (and the `deleted_blobs` queue with
     them), which would orphan the objects in the store. Before the row goes: collect the account's attachment ids —
     `sync_rows` with `entity = 'attachment'` **and** `deleted_blobs` — and `store.delete(objectKey(userId, id))` each,
     best effort (a failure is logged, never blocks the deletion), skipped when `getStore()` is null. Read
     `src/server/attachments/cleanup.ts` and `src/server/storage/index.ts`. Test it against the fs store in a temp dir
     (see `fsStore.test.ts`): two blobs written, account deleted, both gone, another account's blob untouched.
8. **Invite list.** Newest first (`listInvites`). Row: a `key` tile, the label (`admin.invites.noLabel` when null), a
   subtitle by status — active: «creato {date} · scade {date}»; used: «usato il {date} da {email}»; revoked:
   «revocato il {date}»; expired: «scaduto il {date}» — and the status word trailing; non-active rows muted. The
   section's note: «Un codice vale una volta. Si vede solo quando lo crei: al server resta la sua impronta, non il
   codice.» `InviteSummary` gains `createdByName: string | null` and `usedByEmail: string | null` (left joins on
   `user`; the JSON of `GET /api/invites` simply gains two fields).
9. **Invite panel** (`?i=`): status, «Creato {date}, da {name}» (or «dalla riga di comando» when `createdBy` is null),
   «Scade», «Usato da», «Codice: non si rilegge». Active → «Revoca» (asks; `revokeInvite`), and the hint «L'hai perso?
   Revocalo e creane uno nuovo.» with a link to `?new`.
10. **«Nuovo invito»** (`?new`): label (optional, `MAX_INVITE_LABEL_LENGTH`, hint «Solo per te»), «Scade dopo» as a
    `Segmented` of 1, 7, 30, 90 days (7 preselected; the server accepts only these four). `mintInviteAction` returns
    `{ ok: true, code, link, expiresAt, qr: { size, path } }`. The panel then **replaces the form with the minted view
    in client state** — the code never enters a URL, a cookie or storage: «Copialo adesso» alert, the code in a large
    monospaced face, the link (`{PUBLIC_URL}/register?invite={code}`) with «Copia link», «Copia codice», the QR of the
    link, «Scade il {date}», and «Fatto, l'ho copiato», which goes to `/admin/invites` and refreshes. Leaving any other
    way loses the code, which is the point; the alert says so.
11. **The QR** is built on the server, inside the action, by a pure `qrSvgPath(text)` in `src/server/admin/qr.ts`
    (+ test): the `qrcode` package's `create(text, { errorCorrectionLevel: 'M' })` gives the module matrix; the
    function returns `{ size, path }` where `path` is one SVG path of `M{x} {y}h1v1h-1z` per dark module. Read the
    package's own types for the exact shape (`modules.size`, `modules.get(row, col)`) and follow them. The client
    draws `<svg viewBox="0 0 {size+8} {size+8}">` with a 4-module quiet zone. **A QR is dark on light in both themes**
    (an inverted one is not read by every scanner), so it needs two colours that do not follow the theme: add
    `qrDark`/`qrLight` to `@saldo/ui`'s tokens as theme-independent values if nothing like them exists (read
    `packages/ui/src/tokens.ts` and `css.ts`; keep `tokens.test.ts`/`css.test.ts` green, extend them), exposed as
    `--color-qr-dark`/`--color-qr-light`. No hex in a `.module.css` or a `.tsx`.
12. **Istanza**: read-only summary rows, no panel, no chevron: Versione (`APP_VERSION`), Sincronizzazione
    («apiVersion {n} · schema {n}»), Allegati (the driver's name, and `ATTACHMENT_STORAGE={kind}` as the subtitle),
    Indirizzo (`PUBLIC_URL`), Fuso predefinito (`DEFAULT_TIME_ZONE`, with «per chi non ne ha impostato uno»). Section
    trailing text: «dall'ambiente e dalla build». `apiVersion` stops being a literal: `API_VERSION = 1` in
    `src/server/version.ts`, read by `/api/health` and by this page. «Rows skipped by the projection» stays deferred
    (§17.1.2).
13. **Strings.** New keys under `admin.*` (not `web.admin.*`: the namespace exists and the phone will mint invites
    one day), in **all seven catalogs** (`it` is the source; `en`, `fr`, `de`, `sv`, `es`, `pt` translated, same
    `{{variables}}`). Grep before adding: `common.cancel`, `common.close`, `common.delete`, `common.loading`,
    `common.save`, `admin.role*`, `web.auth.emailLabel` and friends already exist. Client components get their strings
    as a typed prop (`src/i18n/adminMessages.ts`, as `tagMessages.ts`), never the root `@saldo/i18n`. Italian source
    text follows the mockup (`docs/superpowers/mockups/2026-09-27-web-admin-variants.html`, variant 3, functions
    `accountPanel`, `mintPanel`, `mintedPanel`, `deleteDialog`, `invitePanel`, `panelsContent`). Counts use `plural()`
    (`@saldo/i18n/translate`) with `_one`/`_other` keys as `tags.uses` does.
14. **Nothing on the phone changes**, and `scripts/user.ts` / `scripts/invite.ts` stay and keep working.
