# 0.3f-3 — Email verification and account recovery

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or
> superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** when the admin has configured SMTP, a new account is sent a link that verifies its email, an existing one
can ask for that link from Profilo, and somebody who lost their passkey gets back in through a magic link sent to a
**verified** address and registers a new passkey. Without SMTP nothing changes: the email stays unverified and there
is no recovery (spec §17.1.4).

**Architecture:** Better Auth does both, as it does the rest of authentication (the 06b decision): its core
`emailVerification` (`/send-verification-email`, `/verify-email`) and its `magicLink` plugin
(`/sign-in/magic-link`, `/magic-link/verify`). Saldo supplies the two send callbacks — which resolve SMTP at call
time through 0.3f-2's `sendMail`, decide **who** may be mailed, and throttle per recipient — and the pages around
them. The browser calls Better Auth's endpoints over HTTP through `authClient`, so both flows sit behind the
instance's one rate limiter and origin check, as `/invite/check` does.

**Tech Stack:** as 0.3f-2. `magicLink` from `better-auth/plugins`, `magicLinkClient` from
`better-auth/client/plugins` (read `node_modules/better-auth/dist/plugins/magic-link/` and
`dist/api/routes/email-verification.mjs` — this plan was written against 1.7.4's source; if the installed version
differs, the library wins and the plan is fixed in the same commit).

Depends on 0.3f-2 (`sendMail`, `mailEnabled`, `instanceName`).

## Decisions

1. **Recovery makes the mailbox as strong as the passkey**, and only on an instance whose admin configured SMTP.
   The spec accepts it (§17.1.4); `SECURITY.md` says it in plain words, with what bounds it: only a **verified**
   address is ever sent a link, a revoked account never is, the link is single-use, stored hashed and lives 15
   minutes, and an admin who does not want it leaves SMTP unconfigured.
2. **`magicLink` is configured so it can only ever sign an existing account in:** `disableSignUp: true` (without it
   the verify endpoint **creates an account** for an unknown address — a way round the registration policy and the
   invites; a test pins that an unknown address ends on the error redirect and the `user` table is unchanged),
   `storeToken: 'hashed'`, `expiresIn: 15 * 60`.
3. **Who is mailed is decided in the callbacks, silently.** `src/server/auth/mailCallbacks.ts` (+ test):
   - `sendRecoveryLink(db, { email, url })`: looks the account up by `lower(email)`; sends only when it exists, is
     **`emailVerified`**, is **not revoked**, and mail is enabled. Every other case does nothing and returns the same
     way. The endpoint answers `{ status: true }` regardless, so the form cannot be used to learn which addresses
     have accounts, or which are verified.
   - `sendVerificationLink(db, { user, url })`: sends when mail is enabled and the address is not synthetic
     (`isSyntheticEmail`).
   - **Neither awaits the delivery.** An SMTP round trip takes visibly longer than doing nothing, which would tell a
     caller what the silence is meant to hide. `src/server/background.ts`: `inBackground(task)` runs the task with
     `after()` from `next/server` when there is a request scope (so a serverless function stays alive until the mail
     is sent) and as a detached promise otherwise; a failure is logged, never thrown. Tests await the task through a
     test hook, not through timing.
   - **Per-recipient throttle**, `src/server/mail/throttle.ts` (+ test, pure, injected clock): at most one message per
     kind per address per 60 s, and five per hour. The rate limiter counts callers; this counts the mailbox, so
     rotating addresses or IPs cannot be used to flood somebody. In memory and per process, like the limiter, and
     documented with the same caveat.
4. **Mail text** in `src/server/mail/messages.ts` (+ test): `verificationMessage(t, { instance, host, url })` and
   `recoveryMessage(t, { … })` → `{ subject, text }`. Plain text: what this is, the link alone on its own line, how
   long it lasts (24 hours; 15 minutes), and «if you did not ask for this, ignore it — nobody gets in without the
   link». Strings under `mail.*` in the seven catalogs. **Language:** the recipient's `settings.language` when they
   have settings and it is not `system`; else the `Accept-Language` of the request that triggered it; else `en`
   (`webLocale` already does the last two steps).
5. **Verification is sent:** (a) after a **new** account is written — `completeRegistration` reports whether it
   created one, and the hook in `auth.ts` then sends, best effort: a mail failure never fails a registration; (b)
   after `POST /api/me/email` fills a synthetic address; (c) on request from Profilo → Account. `expiresIn` 24 h,
   `autoSignInAfterVerification: false` — opening a link must not sign a browser in. The link's `callbackURL` is
   `/email-verified`, a public page in the `(auth)` group: «Email verificata» and a link to the app, or — when the
   library appends `?error=` — «Il link è scaduto o non è valido» and how to ask for another. It is where a phone-only
   user lands too, in whatever browser their mail app opens.
6. **Profilo → Account** (`/profile/account`): the email row's value gains «verificata» / «non verificata». With
   mail enabled, an unverified, non-synthetic address shows «Invia il link di verifica» (a client component calling
   `authClient.sendVerificationEmail({ email, callbackURL: '/email-verified' })`); after it, «Link inviato a
   {email}» and the button is disabled for 60 s. With mail off: «Questo server non invia email: l'indirizzo resta non
   verificato», no button.
7. **Recovery.** `/login` shows «Hai perso la passkey?» → `/recover` **only when mail is enabled** (`mailEnabled`).
   `/recover` (the `(auth)` group, the auth pages' column): the email field and «Manda il link»
   (`authClient.signIn.magicLink({ email, callbackURL: '/profile/passkeys?recovered', errorCallbackURL: '/recover?error=link' })`).
   Whatever the address, the page then says «Se questo indirizzo ha un account con email verificata, abbiamo mandato
   un link. Vale 15 minuti.» With mail off the page says recovery is not available on this server and to ask the
   admin (`pnpm --filter web user …` is the admin's way). `?error=link` says the link expired or was already used.
   `/auth/mobile`'s sign-in gains one line under the button, only when mail is enabled: «Hai perso la passkey? Apri
   {host}/recover in un browser.» — the ceremony the phone waits for cannot be finished by a link opened elsewhere.
8. **After the link** the browser holds a session and lands on `/profile/passkeys?recovered`, which shows an alert
   above the list: «Sei entrato con un link di recupero. Aggiungi una passkey adesso: senza, la prossima volta
   servirà un altro link.» The existing «Aggiungi passkey» does the rest; the lost one can be deleted from the same
   list. An account that has never onboarded is sent to `/onboarding` by `readPage` as always — check the passkeys
   page's path and keep the alert reachable (read how `profile/passkeys/page.tsx` starts).
9. **A revoked account cannot recover.** Two guards, both tested: the callback does not mail it, and the `admin`
   plugin refuses to create a session for a banned user — so a link minted before the revocation dies too. Read how
   the plugin enforces it (`dist/plugins/admin/`) and pin it with a test that drives `/magic-link/verify` for a
   banned account.
10. **Not here:** changing a real address to another (`POST /api/me/email` keeps answering `email_already_set`; with
    SMTP it is now buildable, and is left as a follow-up in `TODO.md`), requiring verification to use the app,
    HTML mail, recovery inside the phone app.

## Rules

As 0.3f-2. In addition: no test sends mail through a socket (the mailer's test transport); a test that needs «mail
enabled» stores an SMTP row through `saveSmtp`.
